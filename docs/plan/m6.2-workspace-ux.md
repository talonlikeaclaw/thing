# M6.2 — Workspace UX, v0.7.1

Target: workspace `0.7.1`, on-disk `FORMAT_VERSION` stays `6`. Nine checkpoints; one per turn under
the AGENTS delivery protocol.

**Status: planned 2026-11-08.** v0.7.0 shipped files, photos, the attachment grid and the library.
Daily use now exposes the next layer of friction: filtering, finding a property, adding or changing
a property, and turning a text column into a real relation. This patch fixes the interaction model
before M7 changes the property model with computed values. It adds no format or dependency; the one
new server operation composes existing property, type, object and view writes.

## Context

The rendered audit at 1440 × 1000 and 390 × 844 found the same problems on both widths:

- **Filtering is a form, not a query.** The Filter button opens a full-width inline band that pushes
  the ledger down. Every condition is three raw controls — a native property select, a native
  operator select, a value input — with a `Needs a value` warning while it is being built. There is
  no property search, no value search, no summary of the active query, and no quick way to ask the
  schedule's own questions (`Overdue`, `Due today`, `This week`). On a phone it is the same inline
  band, not the sheet every other overlay uses.
- **Properties are only managed in two places.** Add property lives on the type page's trailing
  column and in the schema page; the record page's `Properties` header is static. A user reading a
  record cannot add a missing field without leaving it. The type editor's add-property select, the
  columns panel, the filter and sort column selects and the schema lists all enumerate properties
  with no search; a space with 30 properties is a scroll, not a lookup.
- **The schema page is a long stack.** Types and the type editor fill the first screen; the
  property library and property editor sit below them. Selecting a property on a phone means
  scrolling past the type, and then back up.
- **A column cannot become a type.** A text or select column holding `Miles Davis`, `John
  Coltrane`, … cannot be turned into an `Artist` type with one record per value and a relation from
  the album. The only path is manual: create the type, create the records, create a new relation,
  edit every record, then rebuild the views.
- **The phone carries five toolbar controls.** Search, Filter, Sort, Columns and More compete for
  one row; Filter is a full-height panel, Sort and Columns are adjacent panels, and the table moves
  under all of them.

The design language is sound. The problem is the interaction model around it: native selects where
a lookup belongs, inline bands where an overlay belongs, and schema changes that require leaving
the data.

## The interaction model

One sentence: **schema work happens where the data is, and every property is one search away.**

1. **One searchable property picker.** A single component, with the `Property Identity Rule` (accent
   name, format pill), searches name and key, groups "on this type" and "in this space", and works
   as a popover on a fine pointer and a sheet on a phone. Filter, sort, columns, add, manage and the
   command palette all use it. No native property select survives.
2. **Overlays, not bands.** Filter, Sort and Columns open anchored popovers on a fine pointer and
   one `View` sheet on a phone. The table never moves. The filter state is always visible as chips
   under the toolbar; the panel is where it is edited, not where it is stored.
3. **Progressive condition rows.** A condition begins with a property. The operator and value
   appear only after the property is chosen; an incomplete condition stays in the panel and never
   reaches the query. No warning text is needed to explain a draft.
4. **Schema where the data is.** A record page has `+ Add property` and `Manage` on its `Properties`
   header. A type page's column row can open the property editor. The schema page remains the
   library, but it is no longer the only door.
5. **A guided migration, not a hidden format switch.** Turning a column into a relation is a
   three-stage wizard with a preview of every distinct value, every record that will be linked,
   every view that will change, and every filter that will be dropped. The old values remain in
   each record's history; the wizard offers a CSV backup before it runs.
6. **Desktop and phone are the same model, different geometry.** Desktop gets anchored popovers and
   side-by-side lists; the phone gets sheets with a search field, a sticky footer, and a single
   primary action. Both keep the table or record in place.

## Locked decisions

1. **This is `v0.7.1`, not a schema bump.** The promotion reuses the existing `text`, `select`,
   `multi_select` and `relation` formats; no frontmatter key, type key or `FORMAT_VERSION` changes.
   M7 remains the next format milestone.
2. **The filter model stays flat.** AND/OR over conditions, exactly as `Filter` is today. No nested
   groups, no query language, no new filter JSON. A filter that cannot be expressed today is out of
   scope; the interaction gets better, not the grammar.
3. **One picker, used everywhere.** A property is selected from the same searchable list in the
   filter, sort, columns, add, manage and palette surfaces. A second, subtly different picker is a
   defect.
4. **Overlays replace the inline tools band.** Filter, Sort and Columns are popovers on a fine
   pointer and sections of one `View` sheet on a phone. `DESIGN.md` is updated; the table's matte
   ledger and glass chrome do not change.
5. **The record page is a schema surface.** Adding or editing a property from a record writes the
   type (and, where a table view exists, that view) and updates the panel in place. It does not
   navigate to the schema page.
6. **The schema page gets two tabs.** `Types` and `Properties`, with URL state, search in each
   list, and a master-detail phone flow instead of the current stack.
7. **Promotion scope is deliberately narrow.** A source property must be `text`, `select` or
   `multi_select`, and must be carried by exactly one type. The target type is **new**, not an
   existing type. The new relation is a list of records by default. Text splitting on a delimiter
   is opt-in. A shared property is reported as blocking rather than half-converted.
8. **Promotion keeps the original key.** It writes a temporary `<source>_ref` relation, links the
   records, removes the old property, then renames the temporary key back to the source key. Views
   keep the same column key; only the format changes. The old values are in every record's history.
   `is_empty`/`is_not_empty` filters move to the relation; value-bearing text filters cannot be
   translated and are dropped with an explicit warning; sorts and columns move to the new relation.
9. **No new dependency.** Base UI popover/dialog/select, the existing sheet geometry and the
   existing API primitives carry the new surfaces. Search is client-side.
10. **Night Glass is preserved.** The work is structural and interactional; no new visual world, no
    second accent, no decorative motion. The only new visual vocabulary is the searchable picker
    row, the filter chip, the format card and the migration stage list.

## Workflows

### Filtering a view

**Desktop.** Click `Filter` → an anchored glass popover opens under the button. Quick filters sit at
the top for a scheduled type: `Overdue`, `Due today`, `Next 7 days`, `No due date`. Each adds its
condition immediately. Below, the existing conditions are rows: property picker, operator, value;
`Match all` / `Match any` sits above them. The footer reads `Clear all` and `Done`. The table filters
live as conditions become complete. Closing the popover leaves removable chips under the toolbar:
`Room is Kitchen ×`, `Next watering before 8 Nov ×`, `Clear all`.

**Phone.** The same panel opens as a bottom sheet with a sticky header (`Filter`, count) and sticky
footer (`Clear all`, `Done`). The search field focuses without covering the list; the footer sits
above the keyboard. The filter chips are one horizontally scrollable row under the toolbar. The
toolbar is `Search`, `Filter`, `View`; Sort and Columns live inside `View`.

**Values.** Text and number use the existing input; date and datetime add preset buttons (`Today`,
`Yesterday`, `Tomorrow`, `This week`, `Next 7 days`, `No date`) before the input; select and
multi-select use a searchable list of options with checkmarks; relation uses the existing target
search, single or multi; recurrence keeps `RecurrenceInput`; `attachments` keeps only
`is_empty`/`is_not_empty`. An incomplete row is a draft: it shows `Choose a value` but no warning
label and no query.

**Feedback.** The panel header reads `{matched} records match` from the table's current read.
The Filter button keeps its condition-count badge. `Reset` still clears search, filters and sorts.
`Save view` still appears when the query is dirty; on a phone it is also in the sheet footer.

### Adding a property

**From the table.** The trailing `+` header and the Columns panel open the same sheet. The sheet has
two tabs:

- `Existing` — a searchable list of library properties this type does not carry, with format pill
  and key. Select one and `Add to table`.
- `New` — name and a format grid (icon, label, one-line description), not a native select. Choosing
  `Relation` reveals a target-type picker; `New type…` expands name, plural and icon fields and
  creates the type in the same flow. `Several targets` is a toggle.

The three stages become four when a type is created: `type → property → type member → view`. A
visible stage list shows what succeeded; Retry resumes at the failed stage and never creates a
second type, property or member. On success the column appears in the current view.

**From a record.** `Properties` gets `+ Add property` and `Manage`. The same sheet opens without a
view stage; the property joins the type and the record panel appears immediately with an empty
field. If the type has a table default view, the column is added there too. Nothing is written to
the record until the user fills the field and saves.

**Property search on a record.** When a type carries more than eight properties, a search field
appears under the `Properties` header. It filters by name and key, prints `{shown} of {total}`, and
never changes the schema. `Manage` opens the full list in a sheet.

### Managing a property

Every property row can open `Edit property` from its `⋯` menu (record field, columns row, schema
list). The editor is the existing form in a sheet on a phone and a side panel on desktop: name, key
rename, format (read-only with `Turn into a relation…` when eligible), target/cardinality for a
relation, options and colours, usage (types, views, records), and delete. `Remove from this type`
is a separate action in the manage sheet; the space-wide property stays in the library.

The manage sheet lists the type's members with format pills, usage and reorder arrows. It writes the
type members immediately. A member used by a view cannot be removed until the view is changed; the
server's error is shown in the sheet.

### Turning a column into a type

The trigger is `Turn into a relation…` in the property editor and in the columns row menu. It is
enabled for a `text`, `select` or `multi_select` property carried by exactly one type.

1. **Target.** Target type name (`Artist`), plural (`Artists`), icon. Relation name (`Artist`).
   Cardinality defaults to `Several targets` because the ask is a list of records. For text, an
   optional `Split on` field (`;` or `,`) turns one cell into several values; off by default. For a
   multi-select, the source's selected options become targets and the relation is necessarily
   multi.
2. **Preview.** The server computes the plan without writing. The sheet shows: source records
   (live and trashed), distinct values, empty values, target records to create, links, views whose
   columns/sorts will move, filters that will move or be dropped, and any blocking reason. A sample
   table lists the first 20 values with the records that use them and “and N more”. A
   `Download CSV backup` link opens the existing type export before anything changes. Warnings
   require one acknowledgement; blocking errors disable the primary action.
3. **Run.** The stages are `targets → links → finish`, each a server request:
   - `targets` creates the `Artist` type and one record per distinct value.
   - `links` creates the temporary `<source>_ref` relation, adds it to the type, moves the views to
     it, and writes every source record's relation value in one pass.
   - `finish` removes the old property (values stay in history), then renames the temporary key back
     to the source key so views and CSV headers keep their spelling.

   The stage list shows checkmarks and the current count; a failure stops at that stage with a
   `Retry` that resumes. The old property is only removed after every link is written. Closing the
   sheet while a request is in flight is blocked; a failed run can be closed and resumed from the
   property editor.
4. **Result.** The column keeps its name and key, now renders relation chips, and every record's
   old text value is in its history. The target type holds the created records. Filters that used
   the old text column are gone and were named in the preview.

### Checkpoint 6 — Promotion plan and target creation

- New `crates/core/src/promote.rs`:
  - `PromoteOptions { target_name, target_name_plural, target_icon, relation_name, multi, split }`.
  - `PromotePlan { source, target, relation, links, views, warnings, blocking }`, where source
    carries key/name/format/records/distinct/empty, target carries the derived type key and the
    distinct values with their record counts, relation carries the temporary key (`<source>_ref`)
    and cardinality, and views list column/sort moves and filter drops.
  - `plan(index, type_key, source_key, options, target_type?)` validates:
    - the source is a declared `text`, `select` or `multi_select` property;
    - it is carried by exactly one type, and not by a view as `group_by`, `date_property` or
      `cover`;
    - the target type key is free, the temporary key is free, and the relation target is a new
      type; the temporary key is `<source>_ref`, shortened to the 40-character key limit with the
      `_ref` suffix preserved;
    - a `split` is allowed only on text and only with `multi`; a multi-select source requires
      `multi`;
    - the distinct count is at most `MAX_PROMOTE_VALUES = 500`; more is blocking, never a silent
      partial migration;
    - the source record count is at most `MAX_PROMOTE_RECORDS = 5000`; more is blocking;
    - the source key is not `title`, `updated_at` or a schedule key.
    It reads live and trashed objects, maps select option keys to display names, applies the
    optional text split, trims and folds titles for dedupe, and preserves first spelling. It warns
    when the source is required and has empty values (the new relation will be optional), and when
    a select option has no display name. A distinct value longer than the 200-character title limit
    is blocking, never truncated. When `target_type` names an existing type and the expected
    records or temporary property are present, the plan is a **resume** plan: it reports what
    already exists and what remains instead of blocking on the key.
  - `targets(index, plan)` yields the type definition and the target records to create.
- New server route `POST /api/spaces/{space}/types/{type}/promote` [editor] with
  `{ stage: "plan" | "targets", property, target: {...}, target_type?, relation_name, multi,
  split }`. The `plan` stage accepts an optional `target_type` to report a resume; `links` and
  `finish` require the key returned by `targets`, so a retry names the same type rather than
  re-deriving it.
  - `plan` is read-only and returns the plan.
  - `targets` creates the target type with the server's default view, then one record per distinct
    value. It is idempotent by target type key and record title: a retry reuses the type and skips
    records already present. It returns the type key and target ids.
  - A second `targets` request with the same options returns the same ids and creates nothing.
- Tests over temp spaces: text/select/multi-select plans; split; empty values; dedupe by folded
  title; trashed records counted; shared property blocked; target key collision; view warnings;
  target creation idempotence; viewer refused; editor allowed.

**Acceptance:** a plan for an `artist` text column reports 8 records, 6 distinct values, 2 empty,
1 type to create, 6 records to create, 2 views to update and 1 filter to drop; `targets` creates
`Artist` and six records, and a retry creates nothing new.

### Checkpoint 7 — Promotion links, finish and key restoration

- Extend the route with `stage: "links"` and `stage: "finish"`:
  - `links` creates the `<source>_ref` relation property (`format: relation`, `target_type`,
    `multi`), adds it to the type with `featured` copied from the old member and `required` copied
    only when the plan has no empty values (otherwise false), and writes each source object's new
    value in one pass. For each view of the type it moves the column and width from the old key to
    the temporary key, moves sorts, moves `is_empty`/`is_not_empty` filters, and drops value-bearing
    filters; the dropped filters are returned. Each object write appends an `Update` revision, so
    the old value remains in history. The old property is untouched.
  - `finish` removes the old property through the existing store removal (which strips its values
    from live and trashed objects and records each drop), then renames `<source>_ref` back to the
    source key through the existing key-rename path. The old values are already in history; the new
    relation keeps the display name and the final key. It rebuilds the index and broadcasts
    `property.updated`.
  - Both stages are idempotent: an existing relation property is reused, an object that already

## Assumptions & contingencies

- **The filter grammar does not change.** If a request needs nested groups or per-group operators,
  stop and ask; that is a query-model milestone, not this patch.
- **Promotion is the risky checkpoint.** It must stay staged and idempotent. If `links` or `finish`
  cannot be made resumable without a new format or migration marker, stop and split rather than
  shipping a half-converted column. The old property is never removed before every link is written.
- **History is the backup.** The old values are in the prior revision for every object; the wizard
  also offers the existing CSV export before it runs. No hidden backup property is introduced.
- **Only one type may carry the source property.** A shared property is blocked with a sentence
  naming the other types. Converting per type is a later feature.
- **Only a new target type is offered.** Using an existing type needs matching rules for duplicate
  titles and is deliberately out of scope.
- **The property format stays fixed in the normal editor.** Promotion is the one explicit
  conversion path; the editor still refuses a silent format change.
- **No new dependency.** Base UI and the existing sheet primitives cover the pickers and overlays.
- **Night Glass is preserved.** The only visual additions are picker rows, filter chips, format
  cards and the migration stage list; no new world, accent or decorative motion.
- **No physical device is attached.** The v0.4.3 physical-iPhone gate remains open and still
  precedes any keyboard claim.

## What M7 inherits

Computed properties should use the same property picker, property sheet, schema tabs and filter
panel. A computed property is read-only in the picker and the editor, and the promotion action is
disabled for it. Once M7 lands, a promotion whose old property is named by a formula or rollup will
be refused by the existing computed-reference guard; the wizard surfaces that refusal rather than
forcing the removal. M7's `list` result format adds a filter value editor for label lists; the chip
and picker vocabulary does not change. The M7 plan remains at
[`docs/plan/m7-computed-properties.md`](m7-computed-properties.md).
