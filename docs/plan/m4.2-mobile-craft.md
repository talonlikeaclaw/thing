# Milestone 4.2 — mobile craft

Everything below is the v0.4.2 execution spec. Implement top-to-bottom, one checkpoint per turn,
under the delivery protocol in [`docs/ROADMAP.md`](../ROADMAP.md). Read `docs/ROADMAP.md` first,
then this file. M1 is deployed as `v0.1.0`; M2–M4.1 are landed as `0.2.0`–`0.4.1`. Nothing here
re-opens a locked decision.

v0.4.2 is a patch release about one thing: the product on a phone. It adds no route, no file kind,
no server field and no dependency. Every defect it fixes was measured on the running app at
390 × 844 during the audit recorded in §3; the numbers there are the acceptance baseline.

## 1. Scope

In scope:

- **Viewport and keyboard foundation.** `viewport-fit=cover` (today every `env(safe-area-inset-*)`
  in the app resolves to `0`), `interactive-widget=resizes-content`, a `visualViewport` bridge, and
  one sheet primitive that every overlay uses so no dialog can sit under the on-screen keyboard.
- **The command palette on a phone.** Opening it raises the keyboard on the first tap, the results
  list and footer stay above the keyboard, and the search field is the dialog's initial focus in
  both handedness modes.
- **The table's width model.** Saved widths become literal: a drag moves the column under the
  finger by the distance dragged, no other column moves, and the release does not snap back.
- **The table at phone width.** The title column is pinned, cells get enough width to read, the
  pinned action rail stops covering the last column, and the table scrolls in one scroller instead
  of a nested `70vh` box.
- **The type page and the record page at phone width.** Fewer control rows before the first record;
  the record's title is never clipped; identifier chrome and duplicated property keys stop
  competing with content.
- **A touch and text floor across every surface**: 44 px targets, 16 px inputs, no functional text
  under 11 px, no hover-only affordance, no 12 px `<select>` that zooms the page.
- **A physical-device acceptance pass on iOS Safari** — both owners' phones — recorded in the
  checkpoint report, because none of the keyboard behaviour is provable in jsdom or headless
  Chromium. Android has no hardware here; it is asserted from emulation and the documented
  `interactive-widget` behaviour, and the report says so rather than implying a device check.

Out of scope, deliberately:

- **No new page or navigation model.** The bottom bar, its sheet and the routes stay as they are.
  This patch makes what exists work, it does not add an app shell for mobile.
- **No offline, PWA, service worker, install prompt or push.** Those belong to their own milestone,
  and a service worker would change how the SPA is cached while the data layer is still moving.
- **No native gestures** (swipe-to-delete, long-press menus, pull-to-refresh). The one gesture that
  changes meaning is the column resize, and it is removed on phones rather than re-tuned.
- **No new table layout**: the phone table still scrolls horizontally with a pinned title. Stacked
  per-record cards are the rejected alternative (§9) and are not part of v0.4.2.
- **No server change.** The audit found no server-side cause for any of these defects; widths,
  views and the palette all fail in the client.
- **No format change.** `FORMAT_VERSION` stays `4`; no fixture moves.

Success is: on an iPhone, tapping Search in the bottom bar puts the caret in the field **and** the
keyboard up in one tap, the results list is fully visible above the keyboard, `↑/↓/Enter` work; on a
390 px phone the Plants table shows at least two records above the bar, every row keeps its name
while the table is swiped sideways, and nothing reflows mid-scroll; on a desktop a 100 px drag on a
column edge widens that column by 100 px with one request on release and no other column moving;
the table never dims after a resize.

Settled 2026-10-26, before checkpoint 1: the phone table keeps horizontal scrolling with a pinned
title (stacked per-record cards stay out, §8); all eight checkpoints are in scope, including the
type- and record-page restructures; and the keyboard gate in checkpoint 2 runs on the two **iOS**
devices the two users actually own. No Android hardware is available, so Android is covered by
emulation plus the API contract `interactive-widget=resizes-content` defines — and iOS is the
stricter case anyway (§8).

## 4. Contracts

### 4.1 Viewport, safe areas and the on-screen keyboard

`web/index.html`:

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover, interactive-widget=resizes-content" />
<meta name="theme-color" content="#121512" media="(prefers-color-scheme: dark)" />
<meta name="theme-color" content="#f4f3ec" media="(prefers-color-scheme: light)" />
```

`viewport-fit=cover` is what makes the existing sixteen `env(safe-area-inset-*)` uses real;
`interactive-widget=resizes-content` makes Chrome/Android shrink the **layout** viewport when the
keyboard opens, so a `position: fixed; inset: 0` sheet already ends above it. iOS ignores that
meta, so the layout viewport never changes there — `visualViewport` is the only signal.

New `web/src/lib/viewport.ts`:

```ts
/** The keyboard-aware viewport, in CSS pixels of the visual viewport. */
export interface VisualViewportMetrics {
  /** Visible height; equals innerHeight with no keyboard. */
  height: number;
  /** Offset of the visible area from the layout viewport's top (iOS pans). */
  top: number;
  /** Height the keyboard occupies, or 0. */
  keyboard: number;
}

export function metricsFor(vv: { height: number; offsetTop: number }, innerHeight: number): VisualViewportMetrics;
```

The module also exports `subscribeVisualViewport(onChange)` — one `resize` + `scroll` listener pair
on `visualViewport` collapsed into a `requestAnimationFrame` — and `applyViewportMetrics(root, m)`
which sets `--vv-height`, `--vv-top` and `--kb-height` on `document.documentElement`. A React hook
`useVisualViewportVar()` mounts it once in `AppFrame` and removes it on unmount; it is not a context
and nothing re-renders from it. With no `visualViewport` (older browser, jsdom) the CSS falls back to
`100dvh` / `0px`.

`globals.css` gains one sheet geometry, used by every overlay:

```css
.sheet-viewport {
  position: fixed;
  left: 0;
  right: 0;
  top: var(--vv-top, 0px);
  height: var(--vv-height, 100dvh);
  display: flex;
  justify-content: center;
  align-items: flex-end;          /* bottom sheet */
}
@media (min-width: 640px) {
  .sheet-viewport { align-items: flex-start; padding: 12vh 1rem 0; height: auto; inset: 0 auto; }
}
.sheet-popup { max-height: calc(var(--vv-height, 100dvh) - 1.5rem); }
```

Rules that follow from it:

- No overlay may set `fixed inset-0` itself any more; the geometry lives in `.sheet-viewport` /
  `.sheet-popup` so a keyboard change reaches all six overlays at once.
- The **last row** of every sheet (footer, action row, or the popup's bottom padding) carries
  `padding-bottom: max(<existing>, env(safe-area-inset-bottom))`. Padding on the scrolling popup is
  not enough once it scrolls.
- `.settle` becomes `animation-fill-mode: backwards` so the identity transform is dropped when the
  260 ms animation ends. `position: fixed` descendants of a page wrapper must not be affected by a
  finished animation; portals stay as the belt-and-braces.
- Every scrollport gets `overscroll-behavior: contain` (table port, palette list, sheet bodies,
  history list, select popups, board lanes). Page pull-to-refresh is left alone.
- Base layer: `button, a[role], summary, label, [role="button"] { touch-action: manipulation; }` —
  removes the 300 ms double-tap delay and stops a double-tap zoom on controls.

### 4.2 One sheet primitive

New `web/src/components/ui/sheet.tsx` exports `SheetViewport` and `SheetPopup` (thin wrappers over
`Dialog.Viewport` / `Dialog.Popup` that apply the classes above plus the motion), and renders
nothing of its own. Requirements:

- **Motion**: 180 ms `translateY(8px)` + opacity on open, none on close beyond a 120 ms fade; both
  suppressed under `prefers-reduced-motion: reduce`. The palette and capture sheets currently
  appear instantly.
- **Order**: the popup's first focusable stays whatever the caller says (`initialFocus`), so the
  close control's handedness position never decides focus.
- **Migrated in this checkpoint**: `command-palette`, `quick-capture`, `shortcut-sheet`,
  `add-property`, `space-nav` drawer, `sign-out-dialog` (centred variant: `items-center`, no
  keyboard behaviour needed but the same `max-height`).
- **No behaviour change** to trapping, Escape, the backdrop, `finalFocus` or the scroll lock.

### 4.3 Palette focus

Three changes, in this order, all inside `command-palette.tsx` (plus the trigger in
`space-nav.tsx`):

1. **Name the initial focus.** `Dialog.Popup` gets
   `initialFocus={(openType) => (openType === "touch" ? inputRef.current : true)}`. Base UI's
   default deliberately targets the popup container on touch; naming the ref removes that branch
   and, on Android, raises the keyboard on the same frame.
2. **Focus inside the gesture.** Replace the passive effect with `useLayoutEffect` on
   `open === true`, calling `inputRef.current?.focus({ preventScroll: true })`. A layout effect runs
   during the commit that the tap triggered, which is the last moment iOS still counts as the
   user's gesture; the current passive effect runs after paint.
3. **Fallback if, and only if, the device pass in checkpoint 2 shows no keyboard on iOS**: keep the
   portal mounted (`<Dialog.Portal keepMounted>`) and render the sheet off-canvas while closed
   (`data-[closed]:translate-y-full`, `pointer-events-none`, no `display: none`, no `visibility:
   hidden` — both block focus), then call `inputRef.current?.focus()` in the trigger's
   `onClick`/`onPointerUp` **after** `setPaletteOpen(true)`. The field then exists before the tap
   and is focused inside it, which no browser can refuse. This variant is documented in the
   checkpoint report if it is used; it is not adopted speculatively.

The phone entry point is `space-nav.tsx`'s `BarAction` (`aria-label="Search and commands"`); it
must not become a `Dialog.Trigger` — that flips Base UI's `openMethod` to touch and re-enables the
popup-focus branch that item 1 exists to remove.

Palette content on a phone: the result count and the keyboard hint row stay above the keyboard by
construction (§4.1). The hint row stays hidden on coarse pointers, as it is today.

### 4.4 Table width model

Saved widths become literal pixels. The proportional `scale` and the min-flex floor are deleted.

```
saved(key)  = clampWidth(view.widths?.[key] ?? defaultWidth(view, key))   // 80…800, title 240, other 140
fixed       = (showSelect ? SELECT : 0) + (showAddColumn ? ADD_PROPERTY : 0) + actionWidth
sum         = Σ saved(key) for every flex key ("title" + view.columns)
filler      = max(0, port − fixed − sum)                                 // a real, empty trailing column
tableWidth  = fixed + sum + filler
painted(key)= saved(key)                                                  // always, no exceptions
```

- **The filler column** absorbs leftover space so the table exactly fills a wide window and scrolls
  when it cannot. It renders an empty `<col>` plus empty `aria-hidden` `<th>`/`<td>` cells between
  the last property column and the action rail. It is why resizing never moves a neighbour: a drag
  adds `N` to `sum` and removes `N` from `filler`, and every other column keeps its saved width.
- **Drag**: `startWidth = painted(key)` (which is now the saved width, so no jump); the preview is
  `startWidth + dx` in the same units the table paints; commit writes literals. A 100 px drag is a
  100 px column.
- **Commit**: `onCommit` writes the new `widths` map into the type query cache immediately
  (`setQueryData`, no `onMutate` machinery), keeps the preview entry until the PATCH resolves and
  drops it in `onSuccess`. On failure: revert the cache, drop the preview, one toast naming the
  column.
- **No dimming on layout writes**: `writeLayout` must not invalidate `queryKeys.objects(...)`.
  Resize, column visibility and column order update the type only, so `busy` stays false and the
  tbody never gets `opacity-60 pointer-events-none` from a resize.
- **Gesture**: `pointerdown` records the origin and shows no preview until `|dx| ≥ 3`; `pointerup`
  with `|dx| < 3` commits nothing; `pointercancel` clears the preview and the drag; a second
  `pointerdown` while a layout PATCH is pending is ignored (the resizer mirrors `ColumnPanel`'s
  `disabled={layout.isPending}`, which it lacks today).
- **Every resizable header is `relative`** (title included, compact included) so the handle anchors
  to its own cell. This is the fix for the off-screen separator measured at x = 714.
- **No resizers on phones.** `compact` renders no `role="separator"`: a 16 px edge inside a 44 px
  target cannot be found by a finger, it steals the horizontal swipe the hint row tells the user to
  perform, and any accidental `pointerup` currently commits a width. Keyboard steps stay for fine
  pointers. Column widths remain adjustable on a phone through the existing Columns panel on a
  later milestone only if a real need appears — not here.
- **Trailing spacer**: a `<col>` of `actionWidth` after the last property column whenever the action
  rail is sticky right, so the last data column can scroll clear of the rail instead of ending
  underneath it. Body cells for it are empty and `aria-hidden`.

### 4.5 The table at phone width

Compaction threshold stays `port < 640`.

- **Pinned title.** On compact the title cell is `sticky left-0 z-20 bg-ground` for the body and
  `z-30` for the header (above the sticky thead's `z-20`, below nothing else). The title is the row
  identity; the audit's capture shows a horizontally scrolled phone table with five unnamed value
  columns and no way to tell which plant a row belongs to. This reverses the "title scrolls with
  the row" sentence in `DESIGN.md`; the design doc is corrected in checkpoint 8.
- **Widths on compact**: title `136`, property `104`, select `44`, action rail `56` (coarse) /
  `44` (fine). Measured today: title `126`, property `80`. 104 px is the smallest width where a
  12 px mono value shows six or more characters beside the cell padding.
- **No key line on compact.** The `9 px` lowercase key under each header label is the detector's
  finding and is truncated to three characters at 80–104 px; the label alone is the header on a
  phone. `title` attribute and `aria-label` keep the key reachable.
- **One scroller.** On compact the table has no `max-h`; the document scrolls and the `thead` sticks
  to the top of the viewport. On `sm` and up the current `max-h-[70vh]` becomes
  `max-h-[70dvh]`. The port keeps `overscroll-behavior-x: contain` so a horizontal swipe cannot
  become a browser back gesture.
- **Selection must not move the table.** Toggling Select adds the checkbox column and widens the
  scroll range by 44 px, which is unavoidable at the width floor; preserve `scrollLeft` across the
  toggle and move the trigger into the sticky header cell instead of the hint row, so the tap does
  not also change what is under it. The hint row keeps the sentence, minus the resize of the target
  to 46 × 17.
- **The action rail is not data.** At the far right the body's sticky cell gets `z-20` and an opaque
  `bg-ground` (it has `z-index: auto` and a translucent fill today), so it never paints under a
  left-sticky title or over a cell's text mid-swipe.
- **First viewport**: at least two record rows visible above the bottom bar at 390 × 844 with the
  toolbar collapsed per §4.6.

### 4.6 Type page header on a phone

Today the toolbar occupies four rows at 390 px (`Search` / `Filter`+`Sort` / `Columns`+`Save view`+
`Reset` / kebab) and the first data row is under the bottom bar.

- **One row**: a 44 px search icon that expands into the field on tap, then Filter, Sort, Columns,
  and a kebab. `Save view` and `Reset` appear only while the query differs from the saved view, in
  the same row, never on their own line.
- **`View` sheet**: the kebab's three items (View settings, Save as view, Data) move into a single
  sheet labelled **View**, rendering the existing panels. No new surface logic — the same
  components, in a sheet.
- **Header line**: `N RECORDS` and New record on one line; the count no longer wraps under the
  title at 390.
- **Paging footer** renders only when `total > limit` or `offset > 0`; today a single-page table
  still shows "1–4 of 4" plus two disabled buttons under the scrollport.
- **View tabs**: keep the horizontal strip; `+ New view` keeps a 44 px target and its `aria-label`
  when the label is hidden below `sm`.

### 4.7 Record page on a phone

- **Title owns its line.** The `<input>` is full width at 26 px with no sibling in the row. The
  `SAVED` chip moves out of the title row (the sticky bar is the single save indicator), and
  Duplicate joins the overflow next to Revert.
- **Identifier chrome behind a disclosure.** The full UUID and `REV n` collapse into one 12 px mono
  line with a tap target that reveals the full id (copyable) and the revision; phones show the last
  six characters. History keeps the full id.
- **One metadata line** instead of three: `UPDATED <time> · <type>` on phones.
- **No duplicated key.** On `< sm` each property shows its label and value only; the mono key line
  under the label is hidden (it repeats the same word, `ROOM` / `room`). The key stays in the
  `aria-label` and on `sm` and up.
- **Keyboard-safe body.** The body textarea and the sticky save bar use `.sheet-*` geometry rules
  from §4.1: the bar stays above the keyboard (`bottom: calc(var(--kb-height, 0px) + safe-area)`)
  instead of being pinned to the layout viewport's bottom.

## 8. Assumptions and contingencies

- **iOS is the gate, and `initialFocus` + layout-effect focus is the experiment.** Base UI's touch
  branch exists precisely because focusing a field from a dialog's post-gesture focus manager does
  not raise the iOS keyboard; naming the ref and moving the call into the commit gives the best
  chance without restructuring, and the keep-mounted off-canvas variant is the known fallback. Two
  iPhones running different iOS versions is a better sample than one phone of each platform, since
  the strict rule being tested is WebKit's. The milestone does not pretend the emulator proves
  either; the two device lines in checkpoint 2 are the gate.
- **Literal widths mean a wide table can overflow a narrow desktop window**, where today it is
  squeezed to fit. That is the documented behaviour ("narrow screens scroll the table rather than
  reflowing it") and it is what makes a drag predictable. The filler column keeps the common case
  (saved widths sum smaller than the window) flush and gapless.
- **Pinning the title on phones costs about 40 % of the viewport width.** It buys row identity,
  which the audit found missing after any horizontal swipe. Stacked per-record cards are the
  alternative and are rejected for this patch: they would replace the table's whole reason for
  existing — comparing a column across rows — and they are a redesign of a surface `DESIGN.md`
  already specifies.
- **Zooming is still allowed** (`maximum-scale` is not set). Disabling it would break a legitimate
  accessibility need, and the 16 px input floor already removes the accidental zoom on focus.
- **No virtualisation.** Row caps stay at 50 per page; the table is small by construction and the
  milestone does not add windowing.
- **A physical device is required for sign-off.** Both iPhones are available; Android is not, and
  no Android claim is made beyond emulation. If a device becomes unavailable for checkpoint 2, the
  checkpoint stops and reports that rather than claiming a keyboard behaviour from emulation.
- **`interactive-widget=resizes-content` changes Chrome's behaviour for the whole app.** Any
  `position: fixed` element now ends at the resized viewport; that is the intent, but the checkpoint
  pass must look at the toast stack and the sticky save bar specifically.
