# M9.4 — Daily notes

Target: space schema **8 unchanged**, workspace `0.9.3` (the last `0.9.x` before M10 starts). A web
patch: no `space.yml` key, no server route, no dependency, no permission change. It turns the daily
note from a page that opens today into a day-and-month surface. Written 2026-11-23, after `0.9.2`.

**Status: landed as `0.9.3`.** Checkpoints 1–5 landed.

## Why

`/s/:space/daily` is one page (`web/src/pages/daily.tsx`, 175 lines) that resolves
`todayIn(space.timezone)`, reads the day's record through the ordinary list read, creates it once
for an editor and redirects. Everything else about a journal is missing:

| A journal wants | Today |
|---|---|
| Any day, by URL | only today; there is no `/daily/<date>` |
| Yesterday / tomorrow | nothing; the day is fixed when the page loads |
| A month's shape | nothing; `MonthGrid` reaches only the Schedule's calendar and a type's `calendar` *view*, which needs a date property, while a journal records the day in its **title** |
| A reason to keep writing | nothing; no run, no month count |
| The day's context | nothing; an unchecked chore and the note that mentions it never meet |
| Keyboard | nothing; `[`, `]`, `t` are free |

The daily type is a type like any other, so a journal record opened from the table, a search hit or
a link is indistinguishable from any other record — the one piece of structure it has (its title is
a day) is not used anywhere.

## Locked decisions

1. **The format does not move.** Schema 8, no `space.yml` key, no server route. The calendar reads a
   month through the existing list read (two `title` conditions), and the day's schedule through the
   existing agenda range mode (`from`/`to`, already shipped). M10 keeps schema 9.
2. **Title ordering is the contract the calendar stands on.** `filter.rs`'s `Row::compare` already
   compares `Row::Title` with `compare_text`, so `greater_or_equal` / `less_or_equal` on `title`
   work and ISO days sort chronologically. A core test pins it (`titles_order_as_the_daily_calendar_reads_them`);
   no Rust behaviour changes.
3. **The day is the URL; the month is the space's.** `/s/:space/daily/:date` (`YYYY-MM-DD`) opens
   one day and `/s/:space/daily` stays the space's Today (a `replace` redirect to today's day). The
   month and the week are one space Calendar at `/s/:space/calendar` (`?view=month|week`), because
   both dated layers — written notes and due work — belong to the space, not to the Schedule. The
   old `/daily/calendar` and `/agenda?view=calendar` addresses redirect there.
4. **Only today is created by arrival.** `/daily` is the space's standing appointment, so it keeps
   creating today's note once for an editor. Any other day is *offered* — a day card with one
   **Write this day's note** action. Arrow keys must never leave empty notes behind: navigation
   reads, writing is a decision.
5. **A daily note is recognised by its type and its title, and by nothing else.** `record.type ===
   space.daily_type` and `isDayTitle(record.title)`. No new frontmatter key marks a journal entry;
   a note someone renames stops being one, and the calendar simply does not see it.
6. **Stepping is calendar-adjacent, not "next written".** `‹` and `›` mean the previous and next
   day, always, because that is what a reader predicts. Skipping to the last written day is what the
   calendar is for; two behaviours behind one chevron is how calendars start lying.
7. **No prose in the grid.** A cell marks a day as written and shows the note's icon; it does not
   preview the body. `ObjectSummary` carries no body, and adding one would tax every list read in
   the app for one calendar.
8. **One calendar, two shapes.** The month is `MonthGrid` with two optional props —
   `dayMarker(date)` in the cell header and `dayActions(date)` in the day panel footer. The week is
   one card with the same controls, weekday rule and day anatomy: two days per row from `md`
   and seven columns from `xl`, one stacked day per row below `md`, because a column narrower
   than a deadline cannot hold a title beside a verb. Both share
   `CalendarControls` and one `DayDueRow`; a type calendar passes neither extension and is otherwise
   untouched.
9. **The day's schedule is shown, not owned.** Outstanding scheduled rows due on a day come from
   `GET /agenda?from=<day>&to=<day>` (the card) or one range read over the visible month or week.
   Complete and Snooze are the Schedule's own actions with its toasts and Undo; nothing else is
   written and no second due-date model appears. A completed row is not listed because the agenda
   never lists completed rows.
10. **A run is bounded and says so.** `streakOf` runs over a 90-day window ending today — today
    counts when written, otherwise the run ends yesterday, so an unwritten today does not break a
    run before the day is over. A window that is saturated end to end reads `90+` rather than
    inventing a number the read did not see.
11. **All day arithmetic is UTC midnight.** `todayIn(zone)` already gives the space's civil day;
    every shift and grid is built from `Date.UTC`, so no browser zone can move a day, and DST has
    nothing to shift.
12. **Body templates are not here.** A daily note already takes its type's create-time defaults
    (`M9.1`), which is the structured half of a template; the body scaffold lands with record
    templates in M10.2, once `templates/<type>/` exists. No `daily_template` key is invented to be
    replaced two releases later.
13. **The day card is the note's frame, not a page beside it.** An unwritten day renders the record
    sheet the day will become: the record's breadcrumbs, its rail, its identity band and title voice,
    its two columns. Only the middle changes when the note is written, so the reader never leaves one
    page shape for another to start writing, and "not written" is a state of the note rather than a
    separate destination. The day's outstanding rows take the margin a record gives its properties,
    and stay there once the note exists — the margin is the day's, then the record's.
14. **The daily type's New record is today's note.** A type page whose key is the space's
    `daily_type` does not open the capture sheet from its create action: the button reads **Today's
    note** and goes to `/daily`, which resolves today's note or writes it once. A journal's records
    are days, so a blank "New journal" that asks for a title would offer to create the one record
    the calendar cannot address. Creating another day stays a deliberate act: the calendar's day
    panel and the capture sheet (`C`, and the sheet's own type picker) still create any day the
    reader names.

## The day grammar

New `web/src/lib/daily.ts` holds what only a journal needs. The two arbitrary-day helpers already
existed and stay in one place each, beside the caller that first needed them: `shiftDay` with
`todayIn` in `lib/timezone.ts` (both are UTC civil-day math), and `gridRange` with `monthGrid` in
`lib/views.ts` (both are the grid's geometry; it replaced the Schedule's private `gridWindow`).

| Function | Contract |
|---|---|
| `isDayTitle(title)` | exactly `YYYY-MM-DD` **and** a real date: `2026-02-30`, `2026-13-01`, `2026-1-2` and `"2026-02-03 "` are false |
| `shiftDay(day, n)` | `n` days later (negative earlier) over UTC midnights; `shiftDay("2026-03-01", -1)` is `2026-02-28` |
| `gridRange(month)` | the first and last cell of `monthGrid(month)`, inclusive, so a month read covers the leading and trailing days the grid paints |
| `streakOf(written, today)` | the run of consecutive days ending today, else ending yesterday, else `0`; `written` is a `Set<string>` of day titles; `STREAK_DAYS` is the 90-day window a saturated run reads as |
| `dayLabel(day)` | `"Sun 23 Nov"`, `timeZone: "UTC"` |
| `longDayLabel(day)` | `"Sunday, 23 November 2026"`, `timeZone: "UTC"` |
| `monthParam(raw, fallback)` | a valid `YYYY-MM` or the fallback — `?month=` is reader input and is never trusted |

Both labels assemble the parts in that order through `formatToParts`, so a reader's locale changes
the words but never the order. `monthGrid`, `monthOf`, `addMonths`, `monthLabel` and `isMonth` live
in `lib/views.ts` and are reused as they are.

## The routes

| URL | Opens |
|---|---|
| `/s/:space/daily` | replace-redirect to today's day, in the space's zone |
| `/s/:space/daily/:date` | the day's record, or the day card when there is none |
| `/s/:space/calendar?view=month\|week&month=YYYY-MM&week=YYYY-MM-DD` | the space's month or week |
| `/s/:space/daily/calendar` | replace-redirect to the Calendar, keeping the query |
| `/s/:space/agenda?view=calendar` | replace-redirect to the Calendar, keeping month and types |

The day page resolves, in order: not a day → a "That is not a day" state with a link to Today; no
`daily_type` → the existing "no daily note yet" state linking space settings; a `daily_type` that
names no type → the existing missing-type state; a record → `replace` to `/o/:id`; no record →
day card.

**The day card is the note's own frame.** Writing a day must not move the reader to a different
looking page, so the card is the record sheet before the record exists: the same breadcrumbs
(`Space / Journals / 2026-11-22`), the same `components/day-strip.tsx` rail above it, and the same
matte sheet at 24px with the record's identity band — type icon, type name, a mono folio reading
`NOT WRITTEN` where the record puts its id, **the day as the title in the record's title voice**, and
the weekday date where a record prints its dates. One surface either side of the write: pressing
**Write this day's note** changes the sheet's middle and nothing else.

The sheet keeps the record's columns, and the body column opens with the record's own **Body** rule
and its `0 words · 0 characters` count, so the header a reader learns on the card is the one above
the writing well once the note exists. That body column carries the day's state and the action:

- editor, `date === today`: it writes the note once (title, defaults, empty body) and replaces the
  URL with the record, saying **Writing today's note…** while it does;
- editor, any other day: "Nothing written for this day yet." and **Write this day's note**, disabled
  until the day's read and the type's defaults have landed;
- viewer: "An editor can write this day's note." and a link to the type.

The record's property margin carries the day's context: **Due that day** with its count, the
outstanding scheduled rows as links with their type and due phrase, omitted when empty — the same
place a record keeps its properties, so the day's own work is beside the day, not in a second card.
The margin column is drawn only while there is something to put in it (`useDayDue` answers the same
agenda read the band makes, so one request serves both), because a sheet with a blank right half
reads as a broken layout rather than as an empty day; the day card is one full-width column
otherwise.
`components/day-due.tsx` is that list, and it is the same component on the note: the record's
margin is `aside` → the day's band → a rule → Properties, so writing the note never takes the day's
outstanding work away. It is a read (`useAgenda` range mode), so a row completed later drops off
both surfaces at once.

The rail is `‹ Sun 22 Nov` / `Today` / `Mon 24 Nov ›` on one row, the middle slot a link everywhere
except on Today itself, where it is the state it names.

**The type page** of the daily type replaces its create action with **Today's note**, which navigates
to `/daily`; every other type keeps its capture sheet (decision 13).

**The record** of a daily note carries the same rail between the breadcrumbs and the record sheet —
`components/day-strip.tsx` rendered by `pages/object.tsx` only when decision 5 holds, so a renamed
note or another type's record has no day to step. `useDayHotkeys` registers `[`, `]` and `t` while
that surface is mounted (`lib/hotkeys.ts` gains a **Journal** scope and three descriptors, published
through `components/page-shortcuts.tsx` so the `?` sheet advertises them exactly where they work and
nowhere else). All three are reads. The palette gains **Yesterday's note** and **Tomorrow's note**,
each hinting its weekday, and **Calendar** opens the space month.

**The Calendar** resolves its shape from `?view=`, defaulting to the month or the week the reader
   chose last, and reads the visible range:

- month: `useObjects(type=daily_type, filter title ∈ [gridFirst, gridLast], limit 500)` — at most 42
  days, so one page covers it;
- week: the same read over the seven days, Monday to Sunday;
- `useAgenda(from, to)` over the same range, narrowed by `?types=`;
- month only: `useObjects(type=daily_type, filter title ∈ [today−89, today], limit 90)` for the run.

Each cell marks written days with the note's icon and the word **Note** (one chip, `+N more` for a
duplicate), and a quiet `N due` marker when scheduled rows are outstanding that day. The day panel
lists the day's notes and, under them, its outstanding rows; the footer of `dayActions` offers
**Write this day's note** to an editor when the day has none. Above the grid: `12 of 30 days written
in November` and `5-day run`. The nav's Today item stays highlighted across `/daily*`.

## What it is not

No body templates (M10.2), no heatmap by word count, no per-user private notes, no "on this day"
across years, no freeform dashboard. A journal record whose title is not a day is an ordinary
record and is out of scope by decision 5, which the calendar's empty state says in one sentence.

## Manual QA

On the seeded space (journal type with one text field, `daily_type: journal`):

1. `/s/<space>/daily` → today's note; the URL ends at `/o/<id>`.
2. `‹` twice → the day before yesterday; write it; it lands in the journal type and the calendar.
3. A day with no note → day card, **Write this day's note**, one click to the record.
3b. The journal type page's create button reads **Today's note** and opens today's note; a plant
   type's button still opens the capture sheet.
4. `/calendar` → the month; written days marked; a day panel lists the note and the outstanding
   chores and completes one; `Week` → seven days with their notes and due items; the arrows move a
   week, `Today` returns; reload keeps the shape.
5. A phone at 320 px: the strip on one row, the day sheet and the stacked week above the dock, no
   horizontal scroll.
6. A viewer's space: the day card offers no write, the calendar offers no write.
7. `?` while on a journal record lists `[`, `]`, `t` under **Journal**; they do nothing on a plant.

The one check a machine cannot run is the physical-device day sheet on iOS Safari, which stays open
from `0.4.3`.

## Risks

- **Two URLs for one day, and three for the month.** `/daily` redirects to `/daily/<today>`, so the
  canonical day URL is one; `/daily/calendar` and `/agenda?view=calendar` redirect to `/calendar`,
  so the month is one address too. Tests assert the canonical form after the redirect, not before.
- **A day card is a write surface that looks like a page.** It creates only on an explicit click and
  never on mount; a refused write is remembered against the day it was refused on, so stepping away
  and back offers it again with its reason, and a fresh day never inherits the last one's error.
- **A day's read must be settled before it answers.** `useObjects` keeps its last page as
  placeholder data and the day page redirects on a record, so only `isSuccess &&
  !isPlaceholderData` counts: without that check, stepping to a new day opens the previous day's
  note. Every day read the calendar makes needs the same check.
- **A write waits for that read and for the type's defaults.** Three duplicate-note paths were all
  real in the first cut, and each is pinned by a test: the one-per-visit guard resetting on a
  re-mounted effect (StrictMode runs every effect twice, so the second pass wrote again), the guard
  being a mutable flag rather than a fact keyed by the day, and the auto-write firing while the list
  read was still in flight on a warm navigation — the space is cached there, so nothing else delayed
  it. The header action is disabled until both the read and the type's defaults are in, rather than
  swallowing a click made a beat too early.
- **The agenda's range mode omits completed rows.** A past day therefore lists only what is still
  outstanding, and the label says **Due that day** rather than implying a record of what was done.
- **Renamed notes vanish from the calendar.** Decision 5 is deliberate; the empty state and the
  settings sentence are the whole mitigation.
- **The run's 90-day window.** A journal longer than the window reads `90+`; widening it would make
  a page open read a year of summaries, so the bound stays and the copy is honest about it.

## Release note

One sentence under **Unreleased**: the daily note opens any day of its month, steps to yesterday and
tomorrow, and lays the whole month out as a calendar of what has been written.
