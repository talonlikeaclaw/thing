# Milestone 4.1 — everyday-usability follow-ups

Everything below is the v0.4.1 execution spec. Implement top-to-bottom, one checkpoint per turn,
under the delivery protocol in [`docs/ROADMAP.md`](../ROADMAP.md). Read `docs/ROADMAP.md` first,
then this file. M1 is deployed as `v0.1.0`; M2, M3 and M4 are landed as workspace `0.2.0`, `0.3.0`
and `0.4.0`. Nothing here re-opens a locked decision.

v0.4.1 is a patch release, not a new milestone: it collects the friction found in daily use and the
handedness work M4 deferred. It adds no new file kind and no new server surface beyond fields on
two existing resources.

## 1. Scope

In scope:

- **A per-user handedness preference** (`right` default, `left`) that flips every thumb-zone
  surface together: the phone bottom bar, its navigation sheet, shared action rows, toasts, row
  menus and the record/schema save bar. Browser-local, because it describes the device in the
  user's hand, not the space.
- **Add a property from the table**: a trailing column header and the Columns panel both offer
  **Add property**, choosing an existing library property the type does not carry or creating one
  inline with a name and format, then appending it to the current view's columns.
- **Shell and phone polish**: advertise `C` on Capture, align the desktop header cluster to the
  rail's content edge, move Types below the rail links, and keep phone dashboard rows legible.
- **A confirmed sign out**, naming the unsaved-draft risk.
- **Table controls**: first-class Columns beside Filter and Sort, a portalled and flipping select
  option list, and unmistakable ascending/descending indicators.
- **Option-order sorting for Select and Multi-select**, replacing text sort of option keys.
- **Optional record icons**, stored in object frontmatter and shown in the record header, table
  title cells, home recents, palette results, board cards, gallery tiles and Trash.
- **A shared space accent** in `space.yml` (owner-owned), replacing the browser-local per-user
  choice, with a one-time migration from the old local key.
- **Custom accent colours** (`#rrggbb`) alongside the six tested palettes, with legibility checks
  in both schemes and a validation refusal at the API.

Out of scope, deliberately:

- Mirrored pages, RTL text, mirrored icons or a reversed table. Handedness moves actions; it never
  changes reading order or the data layout.
- Drag-and-drop column ordering, column reordering from the table header, or changing a property's
  format after creation. Add property reuses the existing schema and view writes.
- Batch or atomic schema writes. Add property is a short sequence over existing endpoints; a
  partial failure is visible and retryable, not hidden behind a transaction.
- Record icons on the Schedule page, in CSV, in filters/sorts or as a property. An icon is a
  frontmatter field like `title`, not user data a query reads.
- Arbitrary custom palettes with hand-authored ink or separate light values. A custom accent is one
  authored seed; both schemes and the ink are derived.
- Per-member accents. A shared accent is a property of the space, so only an owner changes it.
- A new route, a new dependency, an offline queue or a second value editor.

Success is: on a phone, a left-handed user switches the preference once and finds the bottom-bar
actions, toasts, row menus and Save controls under the left thumb in every surface; from a table,
they add a new Select column, type its first options into cells, reload, and find the property on
the type and the column in the view; sorting that column follows the option order and follows a
reorder in the schema; a record given an emoji shows it in the table, the home, the palette and
Trash; an owner sets a custom accent, every member's open space changes live, and an editor sees it
without being able to change it.

## 3. Dependency and format version

No new Rust or npm dependency. The colour derivation is plain TypeScript and plain Rust; the
picker uses the existing Base UI popover. No new route.

`FORMAT_VERSION` becomes **4**; `MIN_FORMAT_VERSION` stays **1**. One version gates every file kind,
as in M2 and M3:

- `check_schema` accepts `1..=4`; the writer emits `schema: 4` for every file it rewrites.
- Objects and spaces gain one optional key each (`icon`, `accent`). Absent means the current
  behaviour, so every schema-1…3 file stays readable. There is no migration pass.

- `crates/core/tests/fixtures/invalid/schema_4.md` becomes `schema_5.md` with `schema: 5`, and the

- The object icon is part of the object format, so it also joins the revision snapshot (§4.3).
  History lines carry no `schema` of their own; old lines without the new optional field still
  parse.

The workspace and `web/package.json` become `0.4.1` in the final checkpoint.

## 4. Contracts

### 4.1 Handedness

One browser-local preference per user, not per space:

```ts
type Handedness = "right" | "left";
const DEFAULT_HANDEDNESS: Handedness = "right";
// localStorage key
`thing:handedness:${userId}`;
```

- An absent key, malformed value or refused read yields `right`. A refused write is swallowed: the
  choice still applies for the session.
- `applyHandedness(root, value)` sets `data-hand="left"` on the document root in left mode and
  removes the attribute in right mode. `resetHandedness(root)` removes it.
- `AppFrame` reads the key once the signed-in user is known and applies it in a layout effect, so
  the first paint already has the right thumb zone. Cleanup resets the attribute. Signed-out
  surfaces are always right-handed; none of them has a thumb-zone control.
- The preference is available to every role in **Settings > Appearance**, as a two-option radio
  group with an explicit sentence that it changes this browser only. It is not part of the space
  save form and never reaches the server.

Every thumb-zone surface flips together. No surface may be left behind:

| Surface | Right (default) | Left |
|---|---|---|
| Phone bottom bar | space trigger leading, Capture/Search trailing | Capture/Search leading, space trigger trailing |
| Space navigation sheet | close control and Reorder/Done at the trailing edge | same controls at the leading edge |
| `InlineActions` (compact editors, value commit rows) | primary action last, at the trailing edge | primary action first, at the leading edge |
| `StickyActionBar` (record and schema save rows) | primary action last, at the trailing edge | primary action first, at the leading edge |
| Toasts | stack pinned bottom-right | stack pinned bottom-left |
| Compact table row menu | popover `align="end"` | popover `align="start"` |
| Board/gallery card menu | menu anchored to the trigger's trailing edge | anchored to the trigger's leading edge, clamped to the viewport |

Implementation is CSS-attribute driven for alignment, never `direction: rtl` and never
component-wide mirroring. Add one `useHandedness()` context backed by the `AppFrame` state; no
component re-parses storage. `data-hand` on the root drives `justify-content`, insets and menu
alignment.

**Order changes are DOM changes, not CSS `row-reverse` or `order`.** Reversing only the visual
order would make Tab and screen-reader order disagree with the buttons, which is worse than a
right-handed default. `InlineActions` and `StickyActionBar` use a shared `ThumbRow` that takes
`Children.toArray`, reverses the array in left mode, and renders it in that order. Their call sites
keep the canonical right-handed order: secondary and status first, primary last. In left mode the
primary is therefore first in both paint and focus order. Generated children keep stable keys so
React moves rather than remounts them. The mobile bar renders its two groups conditionally in the
same way (trigger then actions on the right; actions then trigger on the left), and the sheet's
title/close row does the same so its close control and focus order move together. Menus change only
their anchor side; their items never reverse. Toasts change only their viewport anchor; their
message/action/dismiss order is unchanged.

Do not animate the switch. Handedness is a persistent setting, not a state transition; an instant
re-layout is correct, and motion here would only delay a task.

Safe areas and targets are part of the mirror. The bottom bar and toasts use
`env(safe-area-inset-left)` / `env(safe-area-inset-right)` in addition to the existing bottom inset,
so neither side tucks under a notch or rounded corner. Every flipped control keeps the existing
44×44px coarse-pointer target and at least 6px of separation; left mode must not compress targets
to fit. No flipped control is hover-only, and the visible focus ring travels with it. Target size
still follows `@media (pointer: coarse)`, not viewport width, so a touch laptop gets the same 44px
controls; handedness is independent of pointer type and applies wherever these surfaces render.

This is an **Operate-mode adaptation**, not a visual redesign: density, type, rules, accent and copy
stay exactly as they are. Text, icons, column order and the rail order are unchanged in both modes.

The primary action is last in the DOM on shared action rows in right mode. This is a deliberate
change from the record save row's current Save-first order: right-handed is the default, and the
default must put Save under the right thumb too, not only the left mode flipping an already-left
layout. Call sites reorder their children once to the canonical secondary-then-primary order; the
left flip is the only place order is reversed.

### 4.2 Add property

Editors only. Two entry points, one dialog:

1. A trailing header cell in the table, after the last visible property column and before Actions.
   It is a `+ Add property` control. On a narrow table it scrolls into view like any column; it is
   never a hover-only affordance.
2. An **Add property** button in `ColumnPanel`, below the visible/hidden lists, opening the same
   dialog.

The dialog offers, in one surface:

- **Existing property**: a select of library properties the type does not declare and that are not
  generated schedule keys. Choosing one and pressing **Add to table** appends it.
- **New property**: Name and Format. The format list is the existing `PROPERTY_FORMATS`. Relation
  defaults to any target type and single-valued; Select/Multi-select start with no options; the
  schema editor remains the place for options, required, target type and multi. Create and add in
  one action.

The write sequence is fixed:

1. For a new property, `POST /api/spaces/{space}/properties` with `{name, format}`. Keep the
   returned key in component state so a retry after a later failure never repeats this POST.
2. `PATCH /api/spaces/{space}/types/{type}` with the whole `properties` list plus
   `{key, required: false, featured: true}`. Inline-added properties are featured: the table is
   where the user added the field, and it must also appear on the record. Existing schema defaults
   (`addProperty` uses `featured: false`) are not reused here.
3. `PATCH /api/spaces/{space}/types/{type}/views/{view}` with `{columns, widths}` from
   `withColumn(view, key, true)`. Only the current view gains the column; other views are
   untouched.

The dialog stays open until all three succeed. On a failure it invalidates the space prefix, names
the stage that failed and keeps the dialog open with Retry; Retry resumes from the current state
(an already-created property is not posted again, an already-added member is not added twice). A
post-creation failure leaves a harmless library property behind and the dialog says so. Success
closes the dialog, shows one toast naming the property, and the table shows the new column with
editable cells. No new API and no format change.

### 4.3 Record icon

`objects/<type>/<slug>.md` gains one optional frontmatter key:

```yaml
schema: 4
id: 0199…
type: plant
title: Monstera
icon: 🪴            # optional; absent means no icon
rev: 3
…
```

- Model: `ObjectDoc.icon: Option<String>`, `#[serde(default, skip_serializing_if = "Option::is_none")]`,
  placed after `title`. `ObjectSummary.icon: Option<String>` copies it. Add `"icon"` to
  `RESERVED_KEYS`, so a property may not use the key.
- Validation does not restrict the glyph beyond the existing icon cleaning (trim, empty becomes
  absent). Reuse `clean_icon` from `routes/mod.rs`; no second emoji catalogue and no server-side
  emoji allowlist. Types and spaces already accept arbitrary emoji strings.
- API: `SummaryJson.icon`, `ObjectJson.icon` and `TrashItem.icon` are emitted only when present.
  `PatchObjectRequest` gains `icon`, using the existing `double_option` shape: absent leaves it
  alone, `null` clears it, a string sets it. A title/properties/body patch that omits `icon` never
  changes it.
- Duplicate copies the icon because it copies the document; Complete preserves it; trash/restore
  preserve it. CSV import/export ignores it: it is not a property and has no header.
- History: `Snapshot` gains `icon: Option<String>` with a default and skip-when-none, so old
  revision lines parse. `snapshot_of` copies it. `changed_keys` reports `"icon"` on the first
  revision when present and on any later change; `revisionDiff` returns the before/after icon and
  the history panel labels it **Icon** and shows the glyphs (or `none`). This keeps the revision
  stream from silently dropping a field M10 restore will need.
- Web: `ObjectSummary`, `ObjectDetail`, `RevisionSnapshot` and `TrashItem` gain
  `icon?: string | null`. The record draft and baseline gain `icon`, so picking an icon marks the
  record dirty and saves with the normal **Save** / `Rev` PATCH; Revert restores it. `IconPicker`
  gains a compact trigger variant for the record header; it keeps the searchable catalogue and
  custom-emoji field.
- Render sites: record header (picker for editors, glyph for viewers), table title cells, space
  home recents (`RecentItem.icon`, stored by `useRecordRecent`), command-palette results
  (`PaletteItem.icon`), board cards, gallery tiles and Trash. Render the glyph only when present;
  an object without an icon keeps its current layout with no empty box. The gallery's type-icon
  fallback in the cover area stays.
- The palette carries icons for types and spaces too, since the component already knows them;
  actions keep no icon slot. Search ranking still uses label and hint text.

### 4.4 Shared accent

`space.yml` gains one optional key:

```yaml
schema: 4
id: 0199…
name: Garden
icon: 🌱
accent: cyan          # a preset id or "#rrggbb"; absent means lichen
timezone: America/Toronto
…
```

- Model: `SpaceMeta.accent: Option<String>` with `#[serde(default, skip_serializing_if = "Option::is_none")]`.
  It stores the authored value, not a resolved colour. `SpaceDetail` exposes `accent: Option<String>`
  and `SpaceSummary` does not; the accent only applies inside a space.
- `PATCH /api/spaces/{space}` accepts `accent` with the same double-option shape as `icon`:
  absent leaves it, `null` clears it to the default, a string validates and normalizes. It stays
  owner-only and uses the existing `space.updated` broadcast and space write mutex. The response
  is the complete `SpaceDetail`, as today.
- Validation lives in the core (`crates/core/src/accent.rs`, §5.1) so the API and the SPA share one
  stated rule and the same test vectors. The server maps a refusal to `422` field `accent`.
  Hand-edited invalid values do not break a space: the client falls back to Lichen and the next
  owner write corrects the file.
- `SpaceLayout` applies `detail.accent ?? DEFAULT_ACCENT` in a layout effect and resets on leave.
  Settings no longer calls `applyAccent` directly; it previews through the same resolved value.
- Settings > Appearance becomes a space setting: the six-option picker and the custom control are
  enabled for an owner and read-only for everyone else, with a sentence that the accent is shared
  with the space. Reset to Lichen is owner-only.
- Migration from the old browser-local key:
  - If `space.yml` has an accent, apply it and delete
    `thing:accent:<userId>:<spaceId>` for this user and space. Stop reading it everywhere.
  - If it has none and the caller is an owner, read the old key once. A non-default value is
    applied optimistically, written through the normal PATCH, and the local key is deleted only
    after that write succeeds. A failure leaves the local key and falls back to Lichen for this
    session; the next load retries.
  - If it has none and the caller is not an owner, apply Lichen. A non-owner's old local value is
    never used to seed the space; the owner owns the shared appearance.
  - `writeAccent` and the per-user round-trip API disappear. The migration reader and a
    `clearStoredAccent` helper are the only remaining local-accent code.

### 4.5 Custom accent colours

The stored value is either one of the six preset ids or a lowercase `#rrggbb`. `#rgb`, named
colours and uppercase input are refused; the server normalizes a valid uppercase hex to lowercase.
`null`/absent means Lichen.

The authored hex is the **dark-scheme accent**. Derivation is normative and identical in Rust and
TypeScript:

1. Parse `#rrggbb` strictly and compute WCAG relative luminance and contrast against the dark
   ground `#121512`.
2. If `contrast(hex, #121512) < 4.5`, refuse the value. A near-black accent cannot be used for
   text and focus on the dark ground, and silently lightening the user's choice is worse than
   saying no.
3. The dark scheme uses the hex unchanged. Its ink is whichever of `#000000` and `#ffffff` has the
   higher contrast against it; requiring `>= 4.5` (which the max of the two always meets) is part
   of the test.
4. The light scheme derives a darker same-hue colour: convert to HSL, lower lightness in 1-point
   steps to 0, and take the first value with `contrast(value, #f4f3ec) >= 4.5`. If none is found,
   refuse; in practice the step to black terminates. Its ink is the better-contrasting of black
   and white, required to be `>= 4.5`.
5. The resolved pair is `{dark:{accent, ink}, light:{accent, ink}}`. Only these four values reach
   CSS.

`web/src/lib/accent.ts` exports `resolveAccent(value: string | null | undefined)` returning the pair
(or the Lichen pair for absent/invalid), `isAccentValue`, the luminance/contrast helpers, and
`applyAccent(root, value)` / `resetAccent(root)`. Applying a preset keeps the existing
`data-accent="<id>"` path. Applying custom sets `data-accent="custom"` plus four inline custom
properties:

```css
:root[data-accent="custom"] {
  --color-accent: var(--custom-accent-dark);
  --color-accent-ink: var(--custom-ink-dark);
}
@media (prefers-color-scheme: light) {
  :root[data-accent="custom"] {
    --color-accent: var(--custom-accent-light);
    --color-accent-ink: var(--custom-ink-light);
  }
}
```

`resetAccent` removes the attribute and the four custom properties. No component reads the custom
value directly; every component keeps using the `accent` / `accent-ink` tokens.

The picker keeps the six preset radios and adds a separate **Custom** form below them: a native
colour input, a `#rrggbb` text field, a live swatch, and an **Apply colour** button (disabled while
invalid or pending). It shows the resolved dark and light swatches so the two schemes are visible
before saving. A refused value shows the server's field message inline and does not change the
space. The accent still marks state only: never body text, never a large surface.

### 4.6 Columns, select options and sort indicators

**Columns button.** For editors, on every non-calendar view, add a ghost button directly beside
Filter and Sort: `Columns` with the `Columns3` icon and the number of visible property columns
(`view.columns.length - 1`, never negative). It uses `aria-expanded` and
`aria-controls="type-columns"`, toggles the existing inline `ColumnPanel`, and keeps whatever the
other panels do when one opens (only one query panel at a time, as today). Remove the Columns item
from the More view actions popover; View settings, Save as view and Data stay there. Calendar views
have no column list and keep no Columns button.

**Select option list.** Replace the absolutely positioned panel in `SelectField` with the installed
Base UI `Popover` primitives: a portalled popup, flip when the space below is short, collision
padding of 8px, and a width that never exceeds the viewport. The popup renders outside the table's
overflow scroller, so the last row's list is whole. Keep the current behaviour intact: filter input
autofocus, type-to-filter by name or key, Enter chooses the first match or creates, Escape closes,
click-outside closes, the Clear row, create-on-type through `useUpdateProperty`, and focus returning
to the trigger. Remove the manual container `onBlur` containment test, which would close a
portalled popup on its first click. No other select surface changes; the record panel and quick
capture inherit the same popup.

**Sort indicator.** The header's arrow slot is fixed-width, so the label never shifts:

- unsorted: a faint `ArrowUpDown` glyph;
- ascending: an accent `ArrowUp`;
- descending: an accent `ArrowDown`;
- `aria-sort` on the header stays `ascending` / `descending` / `none`;
- the button's accessible label names the state and the next action
  (`Sort by Room, currently ascending, activate to sort descending`);
- `title` repeats the state for a pointer;
- the Sort panel's `ascending` / `descending` options and the visible arrow use the same words.

The glyph reflects the effective `sorts` sent to the server, not a local preference. `cycleSort`
keeps its asc → desc → clear cycle; a shift-click still adds or removes that key without disturbing
the others.

## 5. Core changes

### 5.1 New module `crates/core/src/accent.rs`

```rust
pub const ACCENT_IDS: &[&str] = &["lichen", "yellow", "orange", "cyan", "green", "pink"];
pub const DARK_GROUND: &str = "#121512";
pub const LIGHT_GROUND: &str = "#f4f3ec";

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct AccentScheme {
    pub accent: String,
    pub ink: String,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct AccentPair {
    pub dark: AccentScheme,
    pub light: AccentScheme,
}

/// The six presets plus a validated `#rrggbb`, or `None` for a value this
/// build will not use. Input is trimmed and lowercased first.
pub fn resolve_accent(raw: &str) -> Option<AccentPair>;
```

Preset pairs are the existing six palettes, moved next to the validation so there is one spelling
of each value in Rust. Custom pairs follow §4.5. The module exposes the contrast helpers only
inside the crate (or as `pub(crate)`) and is registered in `lib.rs`. Tests cover:

- every preset resolves and meets both floors;
- `#c8d96b`, `#f5a24a`, `#ffffff` and an uppercase `#C8D96B` resolve, with the uppercase normalized;
- `#000000`, `#121512`, `#101010`, `#c8d9`, `chartreuse` and `""` are refused;
- a custom pair meets all four contrast floors in both schemes.

The exact same vectors are duplicated in `web/src/lib/accent.test.ts`. The plan makes the algorithm
normative; if the two implementations disagree, the tests fail on one side.

### 5.4 `query.rs` / `value.rs`

Select and multi-select sorts use option order. Add a comparator that takes the property's
`options`:

- Select (`Value::Text`): compare by the option's position in `PropertyDef.options`; an unknown key
  sorts after every known option and then by `compare_text`; a missing option definition behaves
  the same as an unknown key.
- Multi-select (`Value::List`): compare element-wise by the same option position, then by length,
  exactly like today's element-wise shape. The first differing option decides.
- Any other format, any variant mismatch and the title/updated-at columns keep the existing
  `value::compare` path.
- Direction is applied after the comparator, so descending reverses the option order. Empty
  placement is still applied after direction and is unchanged. The `updated_at`/id tie-break stays.

`query::apply` builds the option-position lookup once per sort key (a `HashMap<&str, usize>` or a
small helper over the `PropertyDef`) rather than scanning the option list on every comparison. It
passes that lookup down with the schema; `value::compare` itself is not given a new parameter that
would force every caller to know about options. Re-sorting after an option reorder is a property of
serving the query fresh: `useUpdateProperty` invalidates the space prefix, and the server recomputes
the order. No client-side reorder and no stored sort index.

## 11. Assumptions and contingencies

- Format 4 is one-way. A v0.4 binary refuses a schema-4 file at `check_schema`; downgrading means
  restoring the data directory. This is the same policy as M2 and M3 and is preferable to a reader
  silently ignoring an icon or accent it does not understand.
- The accent becomes a space property, so members no longer have individual accents. That is the
  point of the change: one shared appearance is predictable and testable. A per-user override
  would be a second source of truth and is not in v0.4.1.
- A custom accent is the authored dark-scheme colour. Colours too dark to read on the dark ground
  are refused rather than silently lightened; the picker says why. The light variant is derived by
  darkening the same hue, which is why one seed is enough and no second stored value is needed.
- The Rust and TypeScript colour implementations duplicate a small pure function. There is no
  shared WASM boundary here; the normative algorithm and identical test vectors are the safeguard.
  If they ever diverge, one suite fails.
- Inline-added properties default to `featured: true`, unlike `addProperty`'s schema-editor
  default. A property added while looking at the table is expected to be on the record too; making
  the user visit Schema to feature it would be the friction this patch removes.
- Add property is not atomic. A failed type or view write can leave an unused library property;
  that is harmless, visible in the library, and the retry path continues where it stopped. A batch
  schema endpoint would need its own conflict rules and is not part of a patch release.
- Handedness is per user per browser, not per space and not synced. The same person on a phone and
  a desktop can choose differently. No server field, no account migration, no RTL.
- The record icon is metadata, not a property: it is not filterable, sortable, CSV-exported or
  shown on the Schedule page. Putting it in a property would give it a key, a format and a second
  writer; the frontmatter field matches how title and body are treated.
- The select popup uses Base UI's installed primitives; no positioning library is added. Its
  collision flipping is browser-verified, and the old absolute panel is deleted rather than kept
  as a fallback.
- `aria-sort` reports the effective query, and the glyph mirrors it. The header never reorders rows
  locally; the server remains the one sorter, so a slow response can show the old order dimmed, not
  a client-side guess.
- Option-order sorting has no stored index. Reordering options changes the next query's result by
  construction, and the property write invalidates the space. This is correct for 500-row caps and
  avoids a denormalized order field in every object.
- Sign out remains a session action, not a draft autosave. The confirmation names the loss; it does
  not add server-side drafts, which remain separate work.
- No new dependency. The custom accent maths, handedness storage and add-property sequence are
  plain code over existing APIs and components.
