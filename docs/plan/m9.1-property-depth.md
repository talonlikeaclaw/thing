## Context

The property model can describe *what* a value is and *how* it reads, and nothing else. Grounded in
the current code:

- **A value has no domain.** `validate_value` (`crates/core/src/validate.rs:594`) checks the
  format's shape — a finite number, a parseable date, a legal option key, a URL, an email, a stored
  file path — and stops there. A `price` column accepts `-5`; a `code` column accepts `hello`; two
  records can carry the same invoice number.
- **`required` exists but cannot be set.** `TypeProperty.required` (`crates/core/src/model.rs:259`)
  is enforced by `validate_object` (`validate.rs:137-145`) and read by the bulk bar and capture, but
  the type editor's membership row renders only remove and reorder
  (`web/src/components/schema/type-editor.tsx:424-456`). Only an API call can set it.
- **A new record starts empty.** `CreateObjectRequest.properties` is whatever the caller sends
  (`crates/server/src/routes/objects.rs:219-235`), and the capture sheet starts with a title and
  every field blank.
- **A rollup aggregates everything its relation names.** `compute.rs:663` walks every resolved
  target; there is no way to say "only the active ones", so a lifetime sum cannot exclude archived
  records.
- **People are not values.** A relation can point at a record; a member is not a record, so "who is
  responsible" has no column. `space.yml` holds `members: [{user, role}]`
  (`crates/core/src/model.rs:541-556`) and the names live in the accounts database.
- **A relation points anywhere in its target type.** Nothing narrows the picker beyond the type, and
  nothing stops two records naming the same target.
- **The formula language stops short of everyday text and date work.** `infer_call`
  (`crates/core/src/formula.rs:730`) and `eval_call` (`formula.rs:994`) implement `if`, `round`,
  `abs`, `min`, `max`, `length`, `lower`, `upper`, `days` and `today`. There is no coalesce, no
  substring test, no replacement, no date arithmetic beyond a difference, and no date formatting.
- **There is no daily note.** `SpaceMeta` has no `daily_type`, and no route opens today's record of
  a type.

The consequence in use: a tracker that cannot refuse a bad value, cannot say who owns a row, cannot
scope a total, and cannot open the page it is opened for every morning.

## Locked decisions

1. **Schema 8 does not move; the half is additive.** Every new key is optional and absent on a
   property or space that does not use it. A `0.9.0` binary cannot read a file that carries one —
   `deny_unknown_fields` reports it as unparseable, the same refusal the format already gives a
   future schema. That is accepted because `0.9.0` is not deployed; a `0.9.1` binary reads every
   `0.9.0` file unchanged. The release notes say so in one sentence.
2. **One owner per concern.** `validation` on the property; `required` and `default` on the
   membership; `filter` on the rollup's `compute`; `target_filter` and `one_to_one` on the relation;
   `daily_type` on the space. No key appears twice, and no rule is enforced in two layers.
3. **Structural refusals are `422`; state refusals are `409`.** `validate_object` stays structural
   and keeps returning `Vec<CoreError>`. A new `validate::conflicts` owns the two cross-record rules
   (`unique`, `one_to_one`) and returns holders; the routes map it to `409` and a CSV file maps it
   to a row problem.
4. **`pattern` is a regular expression through the `regex` crate** — the one new dependency, pinned
   in `[workspace.dependencies]` and inherited by `thing-core`. The crate is linear-time, so a
   pattern a user writes cannot backtrack catastrophically; it is compiled when the property is
   saved (a bad pattern is a `422` naming `validation.pattern`) and matched as a **full match**
   (`^(?:pattern)$`), so `[A-Z]{2}` means exactly two letters rather than a substring.
5. **`unique` names one value.** It is refused on every multi-value format (`multi_select`,
   `attachments`, `recurrence`, `list`, a multi relation, a multi member), so the half never
   invents a set-comparison rule. Two records may both leave the key absent; an absent value is not
   a duplicate.
6. **Defaults are applied by the creation surfaces, never by the server.** Quick capture — which
   every New button opens — and the daily page send the values they show; a cleared default stays
   cleared, duplicate copies its source, CSV writes its cells, the editor's create-from-`[[` row
   stays a title-only stub, and an API client gains nothing it did not ask for. One helper in the
   web applies them, so the two surfaces cannot disagree.
7. **A `member` value stores account ids and reuses the relation's `multi` shape.** Its label
   resolves through the space's member names, and an id that is not a member is kept and reported,
   exactly as a dangling relation is. Sorting and filtering use the stored id, exactly as a relation
   sorts by its id — the label is presentation.
8. **The rollup `filter` reuses the stored `Filter`** and is validated against the target type; the
   evaluator applies it before aggregating. A relation that a rollup reads carries no
   `target_filter` and no `one_to_one`: one narrowing per relation, so the rollup's filter is the
   only thing that decides which targets are aggregated.
9. **`target_filter` is enforced on write, not only in the picker**, so CSV import and an API client
   agree with the UI. **`one_to_one` is enforced on write and answers a `409` naming the holder**;
   the picker is not pre-filtered, because that would need a second read per candidate and the
   refusal is the truth.
10. **The formula additions are `coalesce`, `contains`, `replace`, `date_add` and `format_date`.**
    `length` already exists (`formula.rs:763` checker, `formula.rs:1045` evaluator) and is not
    re-added. `format_date` takes a **literal** pattern of `YYYY`, `MM` and `DD` only: no locale, no
    `strftime`, no second date grammar.
11. **`daily_type` is a space setting naming an existing type; the daily page is a web route over
    the existing list read.** No new API route is added in this half.
12. **The depth half keeps the roadmap's order** — validation, defaults, rollup filters, the member
    format, relation rules, formulas and the daily type, then the release — because each later item
    is built on the earlier ones: a default is validated by `validation`, a member default is a
    member, and the daily page applies defaults.

## The format (schema 8, additive)

### A property's `validation`

`properties/<key>.yml` gains one optional block:

```yaml
schema: 8
key: price
name: Price
format: number
validation:
  min: 0
  max: 500
```

```yaml
key: code
name: Code
format: text
validation:
  pattern: "^[A-Z]{2}-\\d{4}$"
  unique: true
```

| Field | Formats | Values | Absent means |
|---|---|---|---|
| `min` | `number`, `date` | a number, or a `YYYY-MM-DD` string for `date` | no lower bound |
| `max` | `number`, `date` | the same, and `min <= max` when both are set | no upper bound |
| `pattern` | `text`, `url`, `email` | a regular expression, 200 characters at most, compiled as a full match | no shape beyond the format |
| `unique` | every single-value stored format | `true` | repeats are allowed |

Refusals, each carrying the property key (or `validation.<field>`) as the error's `field`:

- `validation` on a calculated property — `a calculated property cannot be validated`.
- `min`/`max` on any other format — `validation.min belongs to number and date properties only`.
- A `min` whose variant does not match the format, or a date that does not parse —
  `validation.min expects a YYYY-MM-DD date`.
- `min` greater than `max` — `validation.min must not be greater than validation.max`.
- `pattern` on any other format — `validation.pattern belongs to text, url and email properties only`.
- A pattern that does not compile, or is longer than 200 characters — `validation.pattern` with the
  compiler's sentence.
- `unique` on a multi-value format — `validation.unique needs a single value`.
- An empty block is written as no block; `unique: false` is written as absent.

### A membership's `default`

`types/<key>.yml` gains one optional field per membership:

```yaml
properties:
  - key: price
    required: true
    featured: true
    default: 0
  - key: room
    required: false
    featured: true
    default: study
```

- The value is validated exactly like a stored value: the format's variant, options, the property's
  own `validation` block, a relation's target type and existence, a member's id shape.
- Refused on a calculated member (`a calculated property cannot have a default`), on a `unique`
  property (`a unique property cannot have a default` — the second create would always be a `409`),
  and on a member of a `list` result.
- `required` plus `default` is legal: the default satisfies the requirement at creation.
- Absent means no default. The field is written only when set.

### A rollup's `filter`

```yaml
compute:
  kind: rollup
  relation: related_plants
  property: height
  aggregate: sum
  filter:
    op: and
    conditions:
      - property: status
        condition: equal
        value: active
```

- `rollup` only; a formula carrying one is `compute.filter belongs to rollups only`.
- Validated with `validate::validate_filter` against the **target type**, rebased to
  `compute.filter`; a condition naming a property the target does not carry is a `422` at property
  save and a `computed_problems` entry when the file is hand-edited.
- The relation must name a target type: a filter over "any type" is refused
  (`compute.filter needs a relation with a target type`).
- An empty filter is written as no filter and passes every target.

### A relation's `target_filter` and `one_to_one`

```yaml
key: caretaker
name: Caretaker
format: relation
target_type: person
one_to_one: true
target_filter:
  op: and
  conditions:
    - property: active
      condition: equal
      value: true
```

- Both are `relation` only; both are refused on any other format.
- `target_filter` is validated against the target type, like a rollup's filter; a relation with no
  `target_type` is refused (`target_filter needs a target type`).
- `one_to_one` requires a single relation (`multi: false`) — `one_to_one needs a single relation`.
- Both are refused on a relation that any rollup reads as its `relation` — `a rollup reads this
  relation; it cannot be narrowed here` (decision 8).

### The `member` format

```yaml
key: caretaker
name: Caretaker
format: member
multi: false
```

- `multi: true` holds a list of ids, exactly as a relation does; `multi: false` holds one.
- A value is an account id (`Value::Text`) or a list of them (`Value::List`); each must parse as a
  UUID. An id that is not a current member of the space is **kept** and reported by the space health
  read, never rewritten.
- `member` is a stored format: it may be `required`, carry a `default`, and be `unique` when single.
- It is not a formula reference, not a rollup `list` target, and not a file-gallery cover.

### A space's `daily_type`

```yaml
schema: 8
id: 018f…
name: Garden
timezone: America/Toronto
daily_type: journal
created_at: 2026-10-21T12:00:00Z
members: []
```

- Optional; absent means the daily page is not offered.
- Must name a type in the space (`422` field `daily_type`), and `null` clears it.
- A hand-edited key that no longer resolves is reported by `/health` as `daily_type` and never
  blocks the space.

### Upgrade path

- A schema-7 or `0.9.0` file parses unchanged: every new key is optional and absent.
- The first write emits `schema: 8` and the keys only when set.
- `crates/core/tests/fixtures/` stays at `schema: 8` and gains: `property_amount.yml` with
  `validation: {min: 0}`; a new `property_code.yml` with `pattern` and `unique`; a new
  `property_caretaker.yml` with `format: member`; `property_related_titles.yml`'s rollup gains a
  `filter`; `space_rooftop.yml` gains `daily_type`; a type fixture's membership gains a `default`;
  and `invalid/` gains one file per refusal class (a pattern on a number, an uncompilable pattern,
  a default on a calculated member, a `one_to_one` multi relation).

## The rules

### Validation

- `min`/`max` compare the stored value: a number numerically, a date as its canonical
  `YYYY-MM-DD` string (text order is date order). A value outside the bound is
  `must be at least 0` / `must be at most 500`, with the property key as the error's `field` — the
  same shape every existing value refusal has, so the cell's toast and the panel's save bar read as
  sentences beside the control that was edited.
- `pattern` runs against the value's text with the compiled full-match regex; a miss is
  `must match ^[A-Z]{2}-\d{4}$` (the pattern as written), the property key as the field.
- `unique` compares with `value::equals(format, a, b)` — the existing rule, so `3` and `3.0` are the
  same number and text compares case-insensitively — over **live** records of the same type,
  excluding the record being written. Trash never blocks a write.
- `validate::conflicts(schema, doc) -> Vec<Conflict>` is the one cross-record check:

  ```rust
  pub enum ConflictKind { Duplicate, TargetTaken }
  pub struct Conflict {
      pub property: String,
      pub value: Value,
      pub kind: ConflictKind,
      pub holder: Uuid,
      pub holder_title: String,
  }
  ```

  A single write answers `409` with the message
  `code must be unique; AB-1042 is already on "March invoice"` and the details
  `{ "reason": "duplicate value", "property": "code", "value": "AB-1042", "holder": { "id": …, "title": … } }`.
- CSV import keeps its own shape: `csv::parse` calls `conflicts` per row and rebases each to
  `CsvProblem { row, field, message }`, plus a per-file set so two rows in one file cannot share a
  unique value (`row 7: code AB-1042 is already on row 3`). The route's existing `422` with
  `details.errors[]` is unchanged.
- The web needs no new error surface: a cell write's failure already toasts `readError`
  (`components/type-table.tsx:269-275`), the record panel shows it inline
  (`components/object-panel.tsx:646`), and quick capture focuses the named field
  (`quick-capture.tsx:296-305`). The messages above are written to read as sentences there.

### Defaults

- `lib/defaults.ts` exports one helper:

  ```ts
  /** The values a new record starts with: every member default the caller did not set. */
  export function withDefaults(
    type: TypeDef,
    properties: readonly PropertyDef[],
    values: Record<string, unknown>,
  ): Record<string, unknown>;
  ```

  It walks `effectiveMembers(type)` in order, skips a key the caller already set (including an
  explicit `null`), skips a computed member, and copies the default. It never mutates its input.
- Quick capture (`components/quick-capture.tsx`) — which the type page's New button, the header and
  the palette all open — and the daily page (checkpoint 12) call it once, immediately before the
  create. The type page itself never creates; it opens capture.
- Quick capture also **seeds its draft** from the defaults, so the field shows the value the record
  will carry; clearing the field sends nothing and the record is created without it.
- The type editor's membership row gains a disclosure with **Required** and **Default**; the default
  editor is the record page's own `PropertyField`, so every format is editable exactly as it is on a
  record. The whole membership list is still written in one `PATCH /types/{key}`. *(Moved by
  [`m9.2-one-property-sheet.md`](m9.2-one-property-sheet.md): the controls now live in the one
  property sheet, which the type editor opens; the write is unchanged.)*

### Rollup filters

- `compute::Evaluator::rollup` (`compute.rs:663`) builds each target's `ObjectSummary::from(&doc)`
  and applies `filter::row_matches(&filter, &summary, &schema)` before the aggregation loop; an
  empty filter passes everything, as it does for a view.
- `count` counts the filtered targets, `sum`/`min`/`max` aggregate their values, `list` lists their
  labels. A target that fails the filter is invisible to the rollup and to every read that shows it.
- The footer, the table cell, the record field and CSV all read the same computed value, so no
  surface needs its own rule.

### The member format

- `PropertyFormat::Member` joins the enum; the compiler forces the arms in `value::parse_value`,
  `value::expected`, `validate::variant_matches`, `SummaryKind::fits` (only `Filled`), `compute::
  value_type`, `compute::format_name` and `csv::parse_cell`.
- `validate_member` checks that each id parses as a UUID and that the shape matches `multi`; it does
  **not** check membership, for the same reason `validate_relation` does not check a target's
  existence: a removed member must never make an unrelated edit impossible.
- Labels: `routes/values.rs` gains `MemberNames` (id → display name) and `Projection` takes it.
  `routes/mod.rs::member_names(&state, &handle)` builds it from `space.yml`'s member ids through
  `accounts.user_by_id`, falling back to the same `Unknown member <uuid>` sentence
  `member_view` already uses (`routes/spaces.rs:469-479`). It is built **before** the index is
  borrowed: it reads SQLite, and the space's index lock must not be held across that read.
  `value_json` renders a member exactly as `relation_json` renders a relation: the joined names, and
  `"missing": true` when an id is not a member. Every handler that builds a projection passes the
  map — the signature change finds them.
- The space health read gains `non_members: [{ property, object, user }]`, computed in
  `routes/spaces.rs::health` where the accounts are reachable; the index stays account-free.
- CSV writes and reads the id, exactly as a relation does; the name is a label.

### Relation rules

- `validate_relation` (`validate.rs:818`) gains: when `target_filter` is set and the target exists,
  `filter::row_matches` must pass, else `<name>: target "X" does not match this relation's filter`.
- `validate::conflicts` gains the reverse scan: for a `one_to_one` relation, another live record
  holding the same target id is a `TargetTaken` conflict; the route answers `409` with
  `{ "reason": "target already linked", "property": …, "target": { "id", "title" }, "holder": { "id", "title" } }`.
- `check_shape` (`routes/properties.rs:551`) validates `target_filter` against the target type,
  refuses both fields on a relation a rollup reads (`compute::relations_read_by_rollups`), and
  refuses `one_to_one` on `multi`.
- `useRelationChoices` (`api/queries.ts:1190`) sends `property.target_filter ?? { op: "and",
  conditions: [] }` as the list read's `filter`, so the picker offers only targets the write will
  accept. The picker does not pre-filter taken targets; the `409` names the holder and the field's
  existing inline error shows it.

### Formulas

Five functions join `infer_call` and `eval_call`; each also joins `FORMULA_FUNCTIONS`
(`lib/formula-hints.ts:13`) and `FUNCTION_HELP` (`components/schema/computed-fields.tsx:147`), which
the type system keeps in step.

| Call | Types | Result | Empty behaviour |
|---|---|---|---|
| `coalesce(a, b, …)` | 2–8 arguments, all the same type | that type | the first argument that is not empty; an unset reference and `""` are empty, `0` and `false` are not |
| `contains(text, needle)` | text, text | checkbox | an unset operand is empty; `""` is contained by every text |
| `replace(text, from, to)` | text, text, text | text | an unset operand is empty; `from: ""` returns the text unchanged; literal, case-sensitive, every occurrence |
| `date_add(date, days)` | date, number | date | a fractional or non-finite `days` is an empty cell; a datetime is refused statically |
| `format_date(date, pattern)` | date, a **literal** string | text | an unset date is empty; tokens are `YYYY`, `MM`, `DD`, any other letter run is a static error naming it, every other character is copied |

- `coalesce` is lazy, left to right: it evaluates an argument only until one is non-empty.
- `date_add` uses `jiff`'s civil-date arithmetic through `schedule.rs`'s existing date helpers; a
  result outside the representable range is an empty cell, never a panic.
- `format_date`'s pattern must be `Expr::Text` in the AST, so the checker can validate the tokens
  before evaluation; a reference in that position is `format_date expects a literal pattern`.
- The evaluator's contract is unchanged: a runtime mismatch is an empty cell, a definition error is
  a `422`.

### The daily note

- `space.yml` gains `daily_type`; space settings offers a type picker to the owner, and the nav
  shows **Today** only while it is set.
- `/s/:spaceId/daily` resolves today's title as `YYYY-MM-DD` in the space's zone
  (`lib/daily.ts::todayIn(timeZone, now)`, one `Intl.DateTimeFormat("en-CA")` call) and reads the
  day's record through the ordinary list read: `type=<daily_type>`, one `equal` condition on
  `title`, sorted by `updated_at` ascending with `limit=1`, so the oldest of a duplicate pair wins.
  If it exists, the page opens it.
- If it does not exist and the caller is an editor, the page creates it once with the day's title,
  the type's defaults and an empty body, then replaces the URL with the record. If the caller is a
  viewer, the page says an editor can create today's note and links the type.
- Two tabs opening at once can create two records with the same title; the type's files are named by
  slug, so both exist and the page opens the oldest. The duplicate is visible and deletable — the
  page does not invent a lock, because the create path is the ordinary one.

## Assumptions & contingencies

- **`regex` is acceptable as the one dependency.** If the reviewer refuses it, the fallback is a
  documented subset (anchors, classes, quantifiers, alternation) hand-written in `validate.rs` —
  which is a new engine, not a smaller change; ask before taking it.
- **A `0.9.0` binary cannot read a `0.9.1` file that uses a new key.** That is the same guard as a
  future schema and is named in the release notes. No downgrade path is built.
- **`unique` scans live records of one type per write.** The index is in memory and the app's scale
  is a personal space; if a space ever grows past the point where an O(n) scan per write hurts, the
  fix is an index-side value map, not a weaker rule.
- **Member names come from the accounts database at request time.** A rename would show on the next
  read; there is no profile rename today, so no cache invalidation is designed.
- **A daily note can be created twice by two tabs.** The page opens the oldest; the duplicate is
  visible and deletable. A server-side find-or-create is deliberately not added (decision 11).
- **`format_date` is numeric-only.** A reader who wants "November 15" gets `DD/MM/YYYY` or
  `YYYY-MM-DD`; a locale-aware formatter is a presentation concern, not a stored formula.
- **The plan may meet a Base UI or `jiff` detail** (a picker that swallows a click, a civil-date
  limit). Settle it in place and record it under **Decisions taken**; do not change a locked
  decision.

## What M10 inherits

M10's view depth builds on this half: a conditional-formatting rule reads `validation`'s bounds and
patterns as its first presets; a saved cross-type query reuses the rollup `filter` and the relation
`target_filter` as its condition grammar; grouping by a member column reuses the label resolution;
and the daily page is the first saved cross-type query, so its list read is the shape M10's
"open a view" route should follow. The member format also gives M12 its assignment UI a column to
write, and M11's agent surface reads `validation` from the same definitions the web does — which is
why `validation` is enforced in the core and not in the web, while `default` stays a creation-surface
convenience an agent may choose to apply.
