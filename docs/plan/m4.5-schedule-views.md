# Milestone 4.5 — schedule views

**Status: planned 2026-10-30, not started.** This is the v0.4.5 execution spec. Implement
top-to-bottom, one checkpoint per turn, under the delivery protocol in
[`docs/ROADMAP.md`](../ROADMAP.md). Read `docs/ROADMAP.md` first, then this file. M1 is deployed as
`v0.1.0`; M2–M4.4 are landed as `0.2.0`–`0.4.4`. Nothing here re-opens a locked decision.

v0.4.5 turns the Schedule page from three server-owned buckets into two views of one schedule: the
**List** it already is and a **Calendar** across every scheduled type, with the view, horizon, month
and type filter remembered per user and space and carried in the URL. It adds **one route
parameter set** to the existing agenda read, no new route, no format or schema change, no core
change, no new dependency and no schema bump. `FORMAT_VERSION` stays `4`.

The work below comes from the landed source and the seeded Garden data; the Calendar does not exist
yet, so there is no live measurement of it. §3 says exactly what was read rather than measured.

## 1. Scope

In scope:

- **One agenda read.** `GET /api/spaces/{space}/agenda` returns a single `rows` array plus
  `later_count` instead of three bucket arrays, takes a `types` filter, and accepts either a
  horizon (`days`) or an explicit date range (`from`/`to`). The List buckets become a client
  projection of the server's `status`; the Calendar asks for the grid's date window.
- **A Calendar view over every scheduled type.** A Monday-first month grid driven by `due_date`,
  with up to three chips per day and a day panel that lists the day's records with their type,
  due phrase, recurrence and the type's completion verb. Completing from the day panel offers the
  same Undo as the List.
- **A view switch.** List and Calendar are two states of the same page, not two routes.
- **Remembered, shareable page state.** `view`, `horizon`, `month` and `types` live in the query
  string; the same state is mirrored to browser-local storage and read back when the URL is bare.
  Refresh, Back and a copied link all land on the same view.
- **A type filter.** One Filter control with a checkbox list of the space's scheduled types, the
  active count, an All/Clear action, and the popover on a fine pointer / the app's sheet geometry
  on a phone.
- **The phone is the same page.** The controls stay above the calendar without covering it, the
  grid respects the bottom bar, and the day panel keeps 44 px targets.

Out of scope, deliberately:

- **No saved space-level views.** The List/Calendar choice is page state, not a `views` entry. No
  cross-type saved view, no board-by-type, no custom filter/sort builder on Schedule. Those wait for
  space-level views.
- **No completed records on the calendar.** A calendar is a plan: a completed one-off leaves the
  page, and a recurring record moves to its next due date. A "show history" toggle is a later
  feature, not this cut.
- **No week or day calendar.** Month only, the same grid the type calendar uses.
- **No agenda route restructure.** `/s/:spaceId/agenda` stays the URL; the nav label stays
  `Schedule`; the nav badge keeps counting the space's overdue records, not the page's filter.
- **No core, format or schema change.** `crates/core/**` is untouched. The server change is the
  agenda read in `crates/server/src/routes/objects.rs` and its tests.
- **No new dependency.** The grid is the existing one, the filter uses Base UI's Popover and the
  existing `SheetPopup`, and the page state is `URLSearchParams` plus `localStorage`.
- **No completion semantics change.** Recurrence, clamping, timezone and the sentence shapes stay
  exactly as M2 and v0.4.4 left them.

Success is: on the seeded Garden space, Schedule opens on List at 14 days as it does today; the
Calendar tab shows every scheduled record on its due day for the current month, including overdue
days, and opens on today; switching to Calendar and back, changing the horizon, browsing months and
filtering to Chore are all in the URL and survive refresh, a copied link and Back; completing a
Chore from a day panel moves the record to its next due date with an Undo; and filtering to a type
shows only that type's rows in both views while the rail badge still reports the whole space's
overdue count.

## 4. The rules this patch follows

1. **One read, one row shape.** The agenda read returns rows the server classified. List buckets
   and calendar cells are client projections of `status` and `due_date`; there is never a second
   copy of the same rows in one response.
2. **The URL is the state; storage is the fallback.** Every non-default view, horizon, month and
   type selection is in the query string. A bare URL reads the remembered state once and then
   rewrites itself with `replace`, so the address bar is always shareable. Every user action pushes
   a history entry, so Back walks the states the user made.
3. **Static defaults decide what the URL omits.** `view=list`, `horizon=14`, the current month, no
   type filter. A shared link cannot inherit the recipient's remembered state, because the sender's
   non-default state is always written out.
4. **The filter narrows the page, not the badge.** The rail badge reports the space's overdue work
   to everyone at every width; it is not a page filter echo.
5. **A calendar is a plan.** Completed records leave it; recurring records re-phase. The List and
   the Calendar therefore agree on what is outstanding.
6. **One month grid, two callers.** The type calendar's grid is extracted, not copied; the type
   calendar's behaviour is unchanged and is re-verified live after the extraction.
7. **No saved views in this cut.** If the page later needs per-type calendars, that is space-level
   views, not another parameter.

### 4.2 Handedness and the visual system

`DESIGN.md` and `.impeccable/design.json` are normative; this page must look and behave like the
rest of the app, not like a new surface. The handedness rule is the one most likely to be missed
when a new surface is written from scratch, because the default `right` mode looks finished:

- **Reading order never moves; thumb-zone actions do.** Only action rows, dialogs/sheets' close
  controls, and menus that open toward a thumb change side. Text, icons, chips and calendar
  columns never mirror.
- **Action rows use `ThumbRow`** (`components/handedness.tsx`), which reverses the DOM so paint, Tab
  and screen-reader order agree. Do not hand-roll `justify-between` plus a conditional reverse.
  Canonical order stays right-handed: secondary/status first, primary last.
- **Sheet and dialog closes follow handedness.** The filter sheet's title row puts its close first
  in left mode, exactly as capture, the palette and the space drawer already do. A sheet with no
  close keeps Escape and its explicit action as the exits.
- **Menus and popovers anchor to the thumb edge.** The type calendar's `CardActions` already does
  this (`anchorLeft` reads `useHandedness()`); any new overflow in the calendar day panel reuses
  that rule rather than pinning left.
- **The Schedule List keeps its compact handedness grid.** v0.4.4's row reverses the title block and
  the verb on a phone; moving the row into `agenda-list.tsx` must preserve it, including the
  `fit-content` column order. The verb stays a separate target from the row link.
- **The new controls are not thumb actions.** The List/Calendar switch, the 7/14/30 horizon and the
  month arrows keep their reading order in both modes; they still meet the 44 px coarse floor.
- **Toasts are already handled** by `:root[data-hand="left"] .toast-stack`; do not re-implement the
  stack, and keep the Undo action inside the toast.

From the visual system, without re-deciding it: tokens only (`text-muted`, `rule`, `bg-raised`,
`rounded-field`, …), never raw colors; the 11 px text floor; 44 px coarse targets and 16 px coarse
inputs; hairline dividers, never cards or shadows; one accent per view; Lucide icons and the app's
type icons, no new icon set. The Schedule calendar must read as the same instrument as the type
calendar: same 6.5 rem day cells, 12 px chips, mono day numbers, label headings and Today treatment.
If a new visual decision turns out to be unavoidable (for example, how a cross-type chip marks its
type), take the smallest one, record it in **Decisions taken**, and write it into `DESIGN.md` while
it is still new — do not leave the design files describing a different world.

Every checkpoint's live acceptance is therefore run at **390 and 1440 in both handedness modes** for
the surfaces it touches, not only in the default. `Account` → Left-handed switches the mode; the
same switch must show the surfaces mirrored exactly once (no double reversal, no moved reading
order).

Before a checkpoint is reported, walk the visual rules once against the new code: tokens not raw
colors, nothing functional below 11 px, 44 px targets and 16 px inputs on a coarse pointer, hairline
dividers, one accent, the primary action at the thumb edge, and both handedness modes checked. A
failure here is a checkpoint failure, not a follow-up.

### Checkpoint 1 — One agenda read: rows, window and type filter

**Files:** `crates/server/src/routes/objects.rs`, `crates/server/src/routes/mod.rs`,
`web/src/api/types.ts`, `web/src/api/queries.ts`, `web/src/components/space-nav.tsx`,
`web/src/pages/agenda.tsx`, `web/src/lib/agenda.ts`, `web/src/lib/agenda.test.ts`.

**Change:**

- The agenda read gains a range mode and a type filter and loses the three bucket arrays. Final
  contract, written into the doc comment above the handler:

  ```
  GET /api/spaces/{space}/agenda?days=14[&types=chore,plant]          [viewer]
  GET /api/spaces/{space}/agenda?from=2026-09-28&to=2026-11-08[&types=…]
  -> { "today": "2026-10-30", "timezone": "America/Toronto",
       "rows": [AgendaRow…], "later_count": 3,             // window mode
       "from": "2026-09-28", "to": "2026-11-08" }           // range mode
  ```

  - `days` keeps its range (`1..=90`) and default (`14`). Mixing modes is refused on the
    parameter's *presence*, not its value: a request carrying `days` together with `from` or `to`
    is a `422` naming `days`; `from` without `to` (or the reverse) is a `422` naming the missing
    field; an unparsable date is a `422` naming it; `to < from` is a `422` naming `to`; a span
    wider than 62 days is a `422` naming `to` (a month grid is at most 42 days; the cap leaves room
    for one cell of slop, not for month-length queries).
  - `types` is a comma-separated list of scheduled type keys. Every key must name a type that is
    scheduled in this space, otherwise `422` field `type`. Absent or empty means every scheduled
    type. Duplicates collapse. The filter is applied before the window and before `later_count`.
  - Row selection: live objects of a scheduled type whose `schedule::state` status is neither
    `Unscheduled` nor `Done`; window mode keeps `days_until_due <= days` (overdue always), range
    mode keeps `from <= due_date <= to` inclusive. `later_count` counts non-`Done` rows with
    `days_until_due > days` in window mode and is omitted in range mode. `from`/`to` are echoed in
    range mode only.
  - Sorting stays `due_date` then `title`. `today`, `timezone` and every `AgendaRow` field stay as
    they are. No core change.
- HTTP tests in `routes/mod.rs`: reuse `chore_space`, `day` and `Server::call` rather than new
  scaffolding. Cover a space with two scheduled types and due days before, on and after both window
  edges; assert inclusive range bounds, that an overdue row before `from` is excluded, that a type
  filter narrows the rows, that `later_count` excludes `Done`, that a completed non-recurring row
  leaves the range, and that each invalid parameter is a `422` naming its field.
- `web/src/api/types.ts`: `Agenda` becomes `{today, timezone, rows, later_count?, from?, to?}`;
  `AgendaQuery` is `{days?} | {from, to}` plus optional `types`.
- `web/src/api/queries.ts`: `useAgenda(spaceId, query)` with the key
  `["space", id, "agenda", query]` (TanStack hashes object keys deterministically) and a URL built
  from the present fields. Only one of `days` or `from`/`to` is ever sent.
- `web/src/components/space-nav.tsx`: the badge reads the overdue count from
  `rows.filter((row) => row.status === "overdue")`; the request stays unfiltered at the default
  horizon, because overdue rows are always inside the window.
- `web/src/lib/agenda.ts`: `agendaBuckets(rows)` returns `{overdue, due_today, upcoming}` by
  filtering `status` and preserving the server's order. Unit-test that it partitions without
  copying order and that it renders the same counts as the old arrays on a fixture. The page uses
  it in place of `schedule.overdue` and friends; every visible string and control stays as it is.
- Do not touch the Calendar, the filter UI or the URL in this checkpoint.

### Checkpoint 3 — Calendar view, view switch and page state

**Files:** `web/src/lib/agenda.ts`, `web/src/lib/agenda.test.ts`, `web/src/pages/agenda.tsx`,
`web/src/components/agenda/agenda-list.tsx` (new),
`web/src/components/agenda/agenda-calendar.tsx` (new),
`web/src/components/views/month-grid.tsx` (consumer only), `web/src/content/changelog.ts`.

**Change:**

- **Page state module.** `lib/agenda.ts` grows the page's state, following `lib/recent.ts`:
  - `AgendaState { view: "list" | "calendar"; horizon: 7 | 14 | 30; month: string }` (`YYYY-MM`),
    `defaultAgendaState(today)` = `list`, `14`, `monthOf(today)`;

    (inclusive; `2026-10` → `2026-09-28`…`2026-11-08`). Unit-test that, the round trip through
    params for every view/horizon/month, that defaults produce no params, and that invalid stored
    JSON is ignored.
- **Page.** Read the state once `useMe`, the space and the types are known: URL over stored over
  default; then `setParams(agendaParams(...), { replace: true })` so the address bar normalizes
  without adding a history entry. Every control change computes the next state, writes storage and
  `setParams(..., { replace: false })`.
- **View switch.** Two pressed buttons (`List`, `Calendar`) in a labelled group beside the title

## 7. Decisions taken while scoping

- **The three bucket arrays are replaced by `rows` on the same route.** A calendar needs a
  date-bounded read; a second array set would be the fourth and fifth copy of the same
  classification. One route, one row shape, one place that knows what a due date means. The
  response shape is an internal API with one consumer; the page and badge are updated in the same
  checkpoint.
- **The filter is server-side.** `later_count` and the rows must agree; filtering the client's
  window would make the footer count the unfiltered space. The type list is validated against the
  scheduled types so a stale key is a field error rather than silently ignored; the page prunes
  stale keys before sending, so the user never sees it.
- **Done records are hidden from both views (settled 2026-10-30).** A completed one-off leaves the
  page; a recurring record re-phases. A history toggle can then be a separate feature with its own
  semantics rather than a quiet exception in this cut.
- **The filter is a popover on a fine pointer and a sheet on a phone (settled 2026-10-30).** One
  trigger with a count scales past a handful of scheduled types without wrapping the page; the
  checkbox list matches the app's other multi-choice surfaces.
- **The calendar day panel completes records (settled 2026-10-30).** The same verb, toast and Undo
  as the List; the shared handler lives in the page so the two surfaces cannot drift.
- **The month grid is extracted, not copied.** v0.4.2–v0.4.4 spent three patches getting the day
  panel, focus return and today scroll right; a second implementation would fork that work.
- **The URL always carries non-default state, and the page normalizes on mount.** A bare link
  cannot express "my remembered month" to someone else, so the state is written out with `replace`
  once and the bar is then always shareable.
- **`types` is comma-joined and sorted.** Stable URLs, one parameter, no JSON-in-a-query habit.
- **The nav badge is unfiltered.** It answers "does this space need me", not "what is on screen".
- **No new route.** `/agenda` gains parameters; no client, doc or test has to learn a second
  endpoint, and the roadmap's "range read" is still a distinct mode of the read.
- **Handedness is a checklist on every new surface, not a redesign.** Only the day panel's action
  row and the filter sheet's close are thumb-zone surfaces; they use `ThumbRow` and the existing
  sheet-close rule. The switch, horizon and month controls keep reading order, because handedness
  moves actions, never navigation or text. Both modes are part of every checkpoint's live pass.
- **AGENTS.md wins where this file is silent.** The delivery protocol, the report shape, the
  no-commit rule, the gate commands, the test placement and the release-note style are inherited,
  not restated differently. The changelog opens as `Unreleased` with the first user-visible
  checkpoint (3) and is promoted to `0.4.5` in checkpoint 5, which is how the file's own comment
  and the release convention meet.
